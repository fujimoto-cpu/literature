I use a Flat Architecture that Codex navigates like a mental map.」人間が見やすいフォルダ階層ではなく、Codex が地図のように navigate できる構造を選ぶ、と。 5 層の中心にあるのが AGENTS.md です。これは Codex が起動時に最初に読む 1 ファイル。原文では「the ‘Global Variable’ of your life」と書かれています。プログラミングで global variable がプロセス全体から参照される変数であるように、AGENTS.md は Codex の全セッションから参照される 1 ファイルです。 中身として書くべきは 3 つ。自分が誰か、今期の目標、絶対に守るべきルール (Non-negotiable Rules)。例えば「Never give me boilerplate」(ありきたりの回答を返すな)「Always check my /notes before suggesting anything」(提案する前に必ず /notes/ を確認しろ) のようなルールです。 ここで一つ補足させてください。Codex の AGENTS.md と、Claude Code の CLAUDE.md は、同じ Markdown ファイルで動きます。書き方も役割もほぼ同じです。両方を Vault のトップに併存させれば、Codex でセッションを開いたときは AGENTS.md が、Claude Code でセッションを開いたときは CLAUDE.md が読まれます。「Codex に乗り換えると Vault を作り直しになる」ことはありません。ツールが変わっても記憶層は同じ Markdown ファイルとして残り続けます。 AGENTS.md の周りを 4 つのフォルダが囲みます。inbox / notes / ideas / projects です。それぞれの役割は次の章で詳しく見ますが、まず Vault 全体のディレクトリツリーを示します。今夜コピペで作れる形にしてあります。 bash ~/Vault/ ├── AGENTS.md # AGENTS.md

Codex 用 master file = 自分の global variable

(Claude Code 用 CLAUDE.md として同内容で併存可)

Who I Am

  • 名前: 自分の氏名
  • 役割: (例) 1 人事業主 / 業務コンサル / マーケ責任者 / R&D マネージャー
  • 利用者: 自分 + (共同経営者 / アシスタント / チームメンバーがいれば明示)
  • 機密扱い: 顧客名と契約条件と売上数値は notes/clients/ と inbox/ のみ。reports/ では匿名化推奨
  • 言語: 日本語が基本。外資クライアント関連は原文 (英語) を保持

2026 Goals

  • Q2 (4-6 月): 主要 3 案件のクロージング + 週次レビューの仕組み化
  • Q3 (7-9 月): 採用 2 名 + ナレッジ Vault の共同編集体制
  • 年間: 個人事業から 3 名チームへ

Non-negotiable Rules

  • Never give me boilerplate (ありきたりの回答を返すな)
  • Always check /notes/ before making any suggestion (提案する前に必ず /notes/ を読む)
  • 顧客名と数値を含む reports/ は外部に出さない
  • 3 ヶ月前の /notes/decisions/ と矛盾する提案を出す前に、必ず私に確認

Vault Layout

  • inbox/ ← 議事録 / Slack スター付き / 商談メモ / ブックマーク取り込み結果が生のまま入る
  • notes/ ← inbox/ を読んで構造化した業務概念ページ (clients / competitors / process / decisions)
  • ideas/ ← 私の判断軸 (why-we-win / pricing-philosophy / hire-criteria / refuse-reasons)
  • projects/ ← 現在進行中の案件 (notes/ の隣に置くことで cross-reference を容易にする) inbox/ は読み取り専用扱い (整理しない、リネームしない、削除しない)。 notes/ と ideas/ と projects/ は Codex が自由に編集してよい。

How to Compile (inbox/ から notes/ への書き方)

  • 1 概念につき 1 ファイル (kebab-case、例: client-A-context.md)
  • frontmatter に sources: [inbox/xxx.md, inbox/yyy.md] と書く
  • 必ず 1 段落以内の定義から始める
  • 関連ページへの wikilink を最低 2 つ
  • 索引: notes/index.md に概念名と 1 行サマリを追記

How to Report (notes/ から reports/ への書き方)

  • ファイル名: {YYYY-MM-DD}_{topic-slug}.md
  • frontmatter に used_notes: […] を必ず書く
  • 結論を冒頭に置く (3 行リード)
  • 出典として参照した notes/ ページへのリンクを末尾に列挙 このファイルが Vault のトップに 1 つ置かれていれば、Codex は新しいセッションを開いたときに最初にこれを読みます。「あなた誰?」から始まる毎朝の儀式が消える瞬間です。 同じ Codex を使っているのに出力品質に差がつくのは、AGENTS.md の有無と質によります。プロンプトの巧さよりも、AGENTS.md にどんな global variable を書いたかが効きます。 では、5 層それぞれに何を入れるのか、業務文脈で具体的に見ていきましょう。 ④inboxはRaw RAMでnotesはSource of Truthでideasは自分の判断軸でprojectsは作業現場 この設計では各層に 1 つずつメタファーを当てています。原文をそのまま引きながら、業務文脈に翻訳していきます。 inbox/ は Raw RAM 原文では「The staging area. Every article, technical doc, or voice note lands here first. No manual filing, no tagging, no friction. This is the ‘Raw RAM’ of your system.」と書かれています。すべての素材が最初に着地する場所、整理もタグ付けも一切なし、と。 業務文脈でいえば、議事録は会議が終わった直後に inbox/ に放り込みます。Slack のスター付き投稿は週末に export して inbox/ に置きます。商談メモは iOS Notes から自動同期します。RFP の PDF は受け取った直後に inbox/ に放り込みます。外部の参考記事は Web Clipper でクリップして inbox/ に。X のブックマークと YouTube の Watch Later は、後述の自動化プロンプトが inbox/ に取り込みます。 ここで自分の判断は一切入れません。整理しようとした瞬間に Vault は失速します。「inbox は触らない」のが鉄則です。 notes/ は Personal Wikipedia / Source of Truth 原文では「Your personal Wikipedia. Once information is processed, it lives here as interlinked facts API schemas, framework deep-dives, and research papers. This is the ‘Source of Truth.‘」と書かれています。inbox/ から処理された情報が、相互リンクされた事実として住む場所、と。 業務文脈で notes/ に育つのは、案件 (clients/)、競合 (competitors/)、プロセス (process/)、意思決定 (decisions/) の概念ページ群です。notes/clients/client-A-context.md は inbox/ にある議事録 5 件と商談メモ 3 件を Codex がスキャンして書き出した「クライアント A の文脈全体像」のページ。notes/competitors/competitor-X-positioning.md は inbox/ の競合分析 PDF と業界 newsletter から Codex が書く「競合 X のポジショニング」のページ。 元記事では研究者向けの例 (API schemas、framework deep-dives) が中心ですが、業務向けでは案件と顧客とプロセスに全置換します。構造は同じです。 ideas/ は自分の判断軸 元の記事では、「This is the most important part. It’s your original thinking and your ‘vibe.’ Storing your unique logic here is what prevents Codex from giving you generic AI answers and forces it to solve problems the way you would.」と書かれています。 つまり、ideas/ に入れるのは外部から仕入れた情報ではなく、自分が考えたこと、自分の判断軸、自分の vibe です。ideas/why-we-win.md には「自社が顧客に選ばれている独自の価値」を書きます。ideas/pricing-philosophy.md には「価格設定で大事にしている思想」を書きます。ideas/hire-criteria.md には「採用で見るポイント」を書きます。ideas/refuse-reasons.md には「受けない案件のパターン」を書きます。 これが Codex の出力品質を決めます。ideas/ が無い Codex は generic な (どこにでもある) 答えしか返しません。ideas/ にあなたの判断軸が入っていれば、Codex はあなたの考え方を真似て答えを書きます。同じ Codex でも記憶設計で差が出るのは、ここに何を書いたかで分かれます。 projects/ は作業現場 原文では「Where the work happens. Because your projects sit next to your notes, Codex can grab an insight from a paper you read three months ago and apply it to the code you are shipping right now.」と書かれています。projects/ が notes/ の隣に置かれていることで、Codex は 3 ヶ月前に読んだドキュメントの insight を今書いているコードに反映できる、と。 業務文脈で projects/ に置くのは、現在進行中の案件、書きかけの提案書、四半期 OKR のドラフトです。projects/client-A-proposal-q2/ には案件 A の提案書ドラフトと相手会社向けの prep メモが入ります。projects/marketing-pivot/ には現在検討中のマーケ方針転換の検討資料が入ります。 これらが notes/ の隣にあることで、Codex に「client-A-proposal-q2 のリードを書いて」と頼んだとき、Codex は notes/clients/client-A-context.md と notes/decisions/2026-04-pricing-strategy.md と ideas/pricing-philosophy.md を全部読みながらリードを書いてくれます。 5 層が揃って初めて、Codex は「あなたの判断軸を持って」「あなたの過去案件を参照しながら」「今の作業を進める」存在になります。 ただ、これを毎日手動で取り込み続けるのは続きません。そこで @ziwenxu_ は「夜の間に Codex が取り込む」仕組みを 4 つのプロンプトで自動化しました。次章で全文を公開します。 ⑤ブクマしてるだけでCodexが夜の間に取り込む4つの自動化プロンプト 元の記事では、ここで保存の摩擦 (Capture Friction) の話を持ち出します。原文では「The number one reason knowledge systems fail is Capture Friction. I built a ‘Passive Ingest’ system so I don’t ‘do’ the work; the pipes do.」と書かれています。Vault が続かない最大の理由は保存の摩擦であり、自分が手を動かすのではなくパイプ (仕組み) を動かす、と。 Browser-use または Computer Use を Codex から起動して、ブラウザの「digital highlights」を 1 日 1 回 scrape します。Browser-use はブラウザを Codex が自動操作するための OSS、Computer Use は画面を見て操作するベータ機能のことです。難しい話に聞こえますが、要は「Codex が代わりに X の Bookmarks ページや YouTube の Watch Later ページを開いて、内容を抽出する」装置です。 読者がやるのは普段通り、X で気になった投稿にブックマークボタンを押す、YouTube で後で見たい動画を Watch Later に入れる、それだけです。「ブクマしてるだけ」が成立する根拠がここにあります。それ以外の取り込み、要約、Markdown 化、inbox/ への保存はすべて Codex が夜間に実行します。 仕組みは 4 つのプロンプトで動きます。コピペで Codex に投入できる形で全文を公開します。 プロンプト 1: X (Twitter) Extraction Prompt markdown “use @computer Navigate to my X Bookmarks. Extract the content of every thread saved in the last 24 hours. Strip out the ads and engagement bait. Convert the core insights into a clean Markdown file titled YYYY-MM-DD-X-Insights.md and save it to my /inbox.” 意訳: 「@computer (画面操作機能) で X のブックマークページに移動して、過去 24 時間に保存されたスレッドをすべて抽出して。広告と engagement bait は削って、中核の insight だけを YYYY-MM-DD-X-Insights.md の Markdown ファイルにまとめて、/inbox に保存して。」 業務向けにカスタマイズするなら、最後の to my /inbox は変えなくて構いません。ただし、ブックマークするときに業務関連 (案件 A / 競合 X / 業界トレンド) のタグを付ける運用を入れると、Codex に「#案件A タグだけ抽出して inbox/2026-05-19_clientA-related.md に保存」のような変則指示も投げられるようになります。 プロンプト 2: YouTube Knowledge Prompt markdown “Access my YouTube with @computer ‘Watch Later’ list. For every video added today, pull the full transcript. Use your internal logic to summarize the technical ‘How-To’ or ‘Big Idea’ from each. Save these as individual Markdown files in my /inbox so I can search them locally.” 意訳: 「@computer で YouTube の Watch Later にアクセスして、今日追加された動画ごとに transcript を全文取得して。各動画から技術的な How-To か Big Idea を要約して、個別の Markdown ファイルにして /inbox に保存して。後でローカル検索できるように。」 業務向けには、社内研修動画や業界カンファ動画の transcript を inbox/ に流し込む用途で使えます。 プロンプト 3: Daily Evolution Prompt markdown “Audit all new files in the /inbox and /notes from the last 24 hours. Cross-reference them with our roadmap in AGENTS.md. MEMORY ENHANCEMENT: Identify new technical patterns or logic I need to internalize for our current projects. EMERGING THESIS: What high-level skill or concept have we mastered this week? ARCHITECTURAL EVOLUTION: Reorganize our folders and concepts to reflect our current level of understanding. Create new specialized directories if our focus has shifted. FIRMWARE UPGRADE: Rewrite the ‘Core Logic’ section of AGENTS.md. Integrate everything we’ve learned this week so you start Monday morning as a more capable, more senior version of yourself.”

意訳: 「過去 7 日間の Daily Brief と新しい情報を分析して。 EMERGING THESIS: 今週マスターした高次のスキルや概念は何か。 ARCHITECTURAL EVOLUTION: 現在の理解水準を反映してフォルダと概念を再構成して。フォーカスがシフトしているなら新しい専門ディレクトリを作って。 FIRMWARE UPGRADE: AGENTS.md の ‘Core Logic’ セクションを書き直して。今週学んだことをすべて統合して、来週のはじめには今週よりも有能でシニアなバージョンの自分として始まるように。」 ここが本当に効くポイントです。Weekly Self-Management Prompt は AGENTS.md (= 自分の global variable) を Codex が自分で書き換える仕組みです。来週の Codex は、今週の業務から学習されたバージョンで起動します。先週よりも少しだけ自分の文脈を深く理解した状態で。 4 つのプロンプトの実装は OSS として GitHub で公開されています (github.com/duolahypercho/codex-knowledge-llm)。Browser-use や Computer Use のセットアップ、cron / launchd を使った夜間自動実行の設定、ファイル監視と通知連携のスクリプトはここを参照してください。本記事は日本の業務文脈での翻訳と AGENTS.md / プロンプトの業務向けカスタマイズに集中しているので、生の実装は OSS リポジトリと役割を分けています。 Browser-use や Computer Use が無くても動かす最小実装はこうです。X のブックマークは手動で copy-paste して inbox/2026-05-19_X-Insights.md に貼り付け、YouTube の Watch Later はブラウザ拡張で transcript を export して inbox/ に置き、Daily Evolution Prompt だけは毎晩手動で Codex に投げる。これだけでも、Daily Brief が生成されて翌朝届く状態には到達します。 ここまでで「夜の間に Vault が育つ仕組み」が手に入りました。ただし、Vault が育つと別の問題が出てきます。Codex が「もう知ってる」と shortcut を取り始める “cocky” 現象です。それを防ぐのが次章の Freshman Rule です。 ⑥Vaultが育つほどCodexが横着になるのを防ぐFreshman Rule 元記事でこう書かれています。「As your vault grows, agents get ‘cocky.’ They take shortcuts.」Vault が育つほど agent は cocky (横着、過信気味) になり、shortcut を取り始める、と。 具体的にはこういう現象です。Vault が 30-50 ページのうちは Codex も毎回 /notes/ を確認します。それが 200 ページに到達すると、Codex は「もう知ってる」「以前 read 済み」を前提に、必要な参照を skip するようになります。3 ヶ月前の意思決定と矛盾する提案を「最新の方が正しい」と勝手に判断して出してくることもあります。元記事の筆者はRule (新入生ルール = 謙虚さの強制) と呼ぶ 3 つを AGENTS.md に追記しています。 Cite the Source 原文では「Tell your agent it isn’t allowed to make a technical decision unless it can link back to a specific file in your /notes. If the info isn’t in the vault, the agent has to admit it’s guessing.」と書かれています。/notes/ の特定ファイルへのリンクが張れない限り技術判断を許さない、Vault にない情報なら agent は「これは推測です」と認めなければならない、と。 業務向けには「/notes/clients/ または /notes/decisions/ にあるファイル名を引用できない限り、案件についての提案を出さない」と書き換えます。 Plan-First Checkpoint 原文では「Never let an agent just start typing code. Non-negotiable Rules (Freshman Rule 追加版)

  • Never give me boilerplate
  • Always check /notes/ before making any suggestion

Cite the Source

技術判断や案件への提案を出す前に、必ず /notes/ の特定ファイル名を引用すること。 Vault に出典がない場合は「これは推測です」と明示して。

Plan-First Checkpoint

提案書 / コード / 戦略ドラフトを書き始める前に、AGENTS.md と関連 /notes/ を 読み、3 文の Battle Plan を書いて私に提示すること。承認後に着手。

Kill the Assumptions

3 ヶ月以上前の /notes/decisions/ と矛盾する判断を提案する前に、agent は 必ず手を止めて私に確認すること。最新が正しいとは限らない。 このセクションを AGENTS.md に追記するだけで、Vault が 200 ページに育っても Codex は「もう知ってる」を理由に shortcut を取らなくなります。半年後の Vault も、初日と同じ謙虚さで動き続けます。 仕組みが揃いました。今週末セットアップしてから 30 日後、6 ヶ月後、12 ヶ月後、Vault はどう変わっていくのか。次章で見ていきます。 ⑦Codexを使うのを辞めCodexを指揮する立場に変わる 30 日目には、inbox/ と notes/ を合わせて 30-50 ページに達しています。毎朝の DAILY-BRIEF.md が安定して届くようになり、Codex に新しい問いを投げるたびに、過去の議事録や Slack スター付きや商談メモが自然に引用される回答が返ってきます。「あの件、先週合意した方向で進めましょう」ではなく、「2026 年 4 月 28 日のクライアント A 議事録 (notes/clients/client-A-context.md:L42) で合意した方向で、競合 X の最新動向 (notes/competitors/competitor-X-positioning.md) を加味して、今週は次の 3 つを進めましょう」と返ってくる質感に変わります。 3 ヶ月目には、notes/ が 100-150 ページに到達し、ideas/ にも 10-15 個の判断軸が蓄積されています。Codex の回答が「業務固有のニュアンス」を持ち始めます。新しい案件の提案書を書く依頼を投げたとき、Codex は ideas/why-we-win.md と ideas/pricing-philosophy.md を読み、過去 3 ヶ月の似た案件の議事録を引きながら、あなたが書いたような提案書を返してきます。一般的な AI 回答ではなく、「あなたの考え方を真似て書いた」提案書です。 6 ヶ月目には、Weekly Self-Management Prompt が AGENTS.md の Core Logic を毎週書き換えてきた結果が積み上がります。今の AGENTS.md は、6 ヶ月前のあなたが書いた初版とはまったく違う、もっと精度の高い「自分の global variable」になっています。Codex は「先週より少しシニアなバージョンの自分」として起動し続けます。 12 ヶ月目には、Vault が個人専用のファインチューニングコーパスとして使えるレベルに育ちます。@ziwenxu_ は元記事の結びでこう書きます。「By the time I sit down at my M4 Mac Mini, my Codex has already spent the night scraping my bookmarks and updating its internal logic.
