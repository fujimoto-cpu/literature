📝 投稿内容

──越境するほど鮮明になる、デザイナーの「核」とは

こんにちは。グッドパッチのUI/UXデザイナーのナスカです。

最近、仕事で「Claude Code」の話を聞かない日がありません。エンジニアはもちろん、デザイナーやPdMも使い始めていて、「AIが実装してくれる」「コードを書かなくても動くものが作れる」という話があちこちから聞こえてきます。

そんな波の中で、私もプロジェクトでClaude Codeを使い始めました。最初は「デザイナーが使うものなのか？」と半信半疑でしたが、気付いたらワークフローがまるごと変わっていました。

この記事は、Claude Codeがどう仕事を変えたのか、やってみたこと、変わったこと、変わらなかったことを正直に書きます。

「デザインは固まっているのに、手が足りない」をきっかけに開発にチャレンジ

APO・デザイナー・フロントエンドエンジニア・バックエンドエンジニア・QAが並走する大規模なスクラムプロジェクトに参画。「デザインの方向性は固まっているのに、エンジニアの工数が足りない」という問題に直面。

VOC（ユーザーの声）を基にしたプロダクトの改善も、優先度の関係でなかなか手が回らない状況を乗り越えるため、デザイナーでありながら初めてフロントエンドの開発に挑戦。

ツールを見直し：Web会議もZoomからGoogle Meetに切り替え、Google Geminiでリファインメントの場で話された内容を文字起こし。その文字起こしや過去のリファレンスを基に、Claude Codeが要件定義書の叩きを自動生成。あとはClaude CodeとUIやUXの要件を対話しながら詰めていく形に。

Claude Code活用の全体像

開発でもデザインでも、何をするにもWhyが大切。「なぜ、この機能が必要なのか」「なぜ、このUIなのか」──その問いを深掘りして問い直し、より良い提案へとつなげていく過程をClaude Codeが時間ごと圧縮してくれるようになった。

Claude Codeを取り入れてワークフローを見直した

フロントエンジニアとモブプログラミングをしながらGitHubの「お作法」を学び、UIコンポーネントからスタイル定義、テストデータまで自分で作れるようになっていった（tsx・Stories・Mockなど）。

似たようなデザインパターンがすでに実装されているもの、コンポーネントの改善、軽微な微調整はClaude Code起点で動かせるようになった。新規画面についてはFigmaで作成し、MCP経由でリンクを共有。Claude Codeが同じコンポーネントを探し、見た目の再現度が高い状態で実装。

Figmaの役割もマスター管理の場から、新しい画面を検討するための場に変化。

AIはGitHubの操作も自動でやってくれますが、コマンドの意味やコードエディタがどういうものかは、最低限理解しておく必要があると思っています。今どんな操作が行われているのか、ローカルとリモートにどんな影響があるのかを把握していないと、AIが何をしているのかが分からないまま進んでしまいます。道具に使われないために、仕組みの輪郭だけは自分で把握しておく。それがAIとパートナーを組む上での必須のスタンスだと感じています。

AIが作業を回してくれている間に、Slackの返信やプロジェクト外のタスクなど、小さいサブタスクが並行して回せるようになり、動ける範囲が広がった。

デザイナーに求められる「評価」の役割 チームのデザイン品質も仕組み化

バイブコーディングで誰もがアウトプットを出しやすくなった今、それを評価できる目の価値が上がっている。

非デザイナーがUIを作る機会が増えているのに、自分でデザインを評価できる仕組みがない問題に気付き、品質チェックのGemを作成。JIS、デザイン原則、プロダクト固有のガイドライン、アンチパターンといったチェック要素を組み込み、非デザイナーでも使いやすい形に。さらに実装の場でも活用できるようにスキル化してClaude Codeとの開発フローに組み込んだ。

ディレクトリ構成の例

グッドパッチのデザインシステム「Sparkle Design」の土台があることで、品質の高い「いいデフォルト」が用意されているので、ゼロから設計しなくてもすぐ使える状態からスタートできる。

社内スキル共有サービスも活用：デザインレビュー、コードレビュー、議事録作成、PRの文章生成……チームや個人の「やり方」を言語化して、再利用可能な形にまとめたスキルをインストールできる。「誰かのノウハウ」を「チームの資産」に変える仕組み。

境界が融けるほど、デザイナーの「核」が鮮明になる

越境する中で気付いたこと：実装ができるようになっても、自分の中でずっと変わらない問いがある。

例えばAIのアウトプットを見たとき、「このグレーの色、もう少し調整できないか」「この角丸と余白のバランスが気になる」と思ってしまう。これはスキルではなく「自分が納得できるか」という基準、いわば「審美眼」のようなものです。こうしたレビューは、引き続きデザイナーがやる必要があるのでしょう。

AIにはできないこと：

  • Why（なぜやるのか）、What（どんな価値を提供したいのか）、How（それをどう提供するのか）の要件整理
  • 現場に行き、実際にユーザーになって使うなど、一次情報を取りにいくこと
  • ユーザーが置かれている状況や、その場の感情の機微の把握

「デザイナーが手掛ける領域は『デザイン』だけではない」と「ユーザー体験の責任を持つのはデザイナーだ」は一見矛盾しているように見えるが整合している。越境するほど、核として守るべき領域が逆に鮮明になっていく。

生成AIが普及しても、ユーザー体験の責任を持つのは「人間」に変わりはない

AIが普及しても、サービスやプロダクトに込められた想いを届けるのは人間に変わりはない。たくさんのリファレンス、AIのデータ、ユーザーの声──いろんな文脈を理解した上で、最後に決めるのは人間。

役割や職種の境界が融けたとしても、最後に体験の責任を取るのは誰か。自分はデザイナーだと答える。

引用元：Goodpatch Blog（2026.5.25）

📝 要約

🎯 GoodpatchのUI/UXデザイナー（@nazcadon）が、Claude Codeをデザイン×開発の現場に取り入れた実体験レポート。要件定義自動生成・Figma MCP連携・品質チェックGem作成まで実践し、「越境するほどデザイナーの核（審美眼・ユーザー体験責任）が鮮明になる」という気づきを語る。

📌 ポイント

Claude Codeによるデザイナーの越境

文字起こし→要件定義書自動生成→FigmaのMCP連携→tsx/Stories/Mock実装というワークフローを確立。デザイナーが実装できるようになることで、エンジニアの工数不足問題を自力で解決できるようになった。

品質チェックGem + スキル化で組織課題を解決

「バイブコーディングで非デザイナーもUIを作れる時代」に対応し、JIS・デザイン原則・アンチパターンを組み込んだ品質チェックGemを作成してClaude Codeに統合。「誰かのノウハウ→チームの資産」化の仕組みを実装した。

審美眼・ユーザー体験責任はAIに代替不可

AIのアウトプットを「これ違う」と感じられる審美眼、一次情報取得（現場・ユーザーへの共感）、WHY/WHAT/HOWの要件整理はデザイナーが守るべき核。越境（領域拡張）するほど守るべき核が鮮明になる逆説的発見。

ゆりこさんへの活用提案

② AI推進発信のフレームに活用 「デザイナーの越境＋審美眼は代替不可」というメッセージは、KONNEKT社内AI推進でゆりこが語る際のフレームとして使える。「AIで楽になる×CDとしての価値は上がる」という二軸の言語化。
