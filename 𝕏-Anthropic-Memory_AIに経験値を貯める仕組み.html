🧵 スレッド冒頭

Anthropic公式が「AIに経験値を貯めて進化させる方法」暴露してて、普通に革命起きてるんやがwww

もはや英語圏のClaude Code勢だけ先に別ゲー始まってるし、今までのAIとはレベル違うで…

日本語でまとめたから時間あるとき読んで⤵︎ 数ヶ月後一気に広がりそうやから、先に知りたい人はブクマ推奨

【まず前提の用語だけ押さえて】

このスレッドに出てくる言葉、これだけ知ってればOK↓

  • Memory ＝AIが作業中に学んだことを保存して次回以降に使う仕組み
  • Managed Agents API ＝Anthropicが提供する、本番用エージェントを動かすAPI
  • Dreaming ＝複数エージェントの作業ログを見て、共通の失敗や成功パターンを自動で記憶に反映する新機能
  • Memory Store ＝AIが読み書きする記憶の保存場所
  • Permission Scope ＝記憶に対して「読むだけ」「読み書きOK」を分ける権限設定
  • Optimistic Concurrency ＝複数AIが同時に記憶を書き換えても、上書き事故を防ぐ仕組み
  • Version History ＝誰が・いつ・どんな記憶を更新したか全部追える履歴

【1つ目】今回の発表の核心：「AIに経験値を貯めさせる」が始まった

登壇したのはAnthropicのPlatform Team PM、Mahes

これまでAnthropicはAIエージェント用にいろんな部品を出してきた↓

  • MCP：外部ツールやデータに繋ぐ
  • Claude Code：コード作業を任せる
  • Agent SDK：エージェントを作る
  • Skills：AIに新しい能力を追加する

でも、まだ足りなかったものがある

それが「Memory」 つまりAIが作業経験から学び、次の仕事で賢くなる仕組み

【2つ目】今までのAIは「毎回ほぼ初対面」だった

普通のAIは、毎回プロンプトに全部説明しないといけない

  • この案件では何が成功条件か
  • 前にどんなミスをしたか
  • このコードベースの癖は何か
  • どの手順がうまくいったか
  • どの調査はもう終わっているか

これを毎回人間が教える必要があった

でもMemoryがあると、AI自身が作業しながら 「これは次回も使える」 「この失敗は覚えておくべき」 「この環境ではこの手順が正解」 みたいに経験を蓄積できる

ここが今までのAIと根本的に違う

【3つ目】MemoryでAIが覚えられること

Anthropicが想定してるMemoryの中身はかなり実務寄り

AIが覚えるもの↓

  • タスクの成功条件
  • よくある失敗
  • うまくいった戦略
  • 使っているコードベースの構造
  • 更新すべきファイルやアセット
  • 過去の調査結果
  • 他のAIエージェントが学んだこと

つまり単なる「会話履歴」じゃない AIが現場で働いた経験を、次のAIや未来の自分に引き継ぐための仕組み

これがあると、AIが使い捨て作業員から「育つメンバー」になる

【4つ目】一番ヤバいのは「他のAIから学べる」こと

Mahesが特に興奮していたのがここ

複数のAIエージェントが同じ環境で働いているとする

例↓

  • あるAIがコード修正
  • 別のAIが障害調査
  • 別のAIがテスト作成
  • 別のAIがドキュメント更新

それぞれが別タスクをやりながら、同じMemory Storeに学びを残せる

すると次のAIは 「前のAIが何を調べたか」 「どこで失敗したか」 「何が原因だったか」 を読んでから動ける

これ、もはやAIチームに集合知が生まれてる状態

【5つ目】すでに効果が出てる：初回ミス90%減

AnthropicはManaged AgentsでMemoryをパブリックベータとして提供開始済み

早期ユーザーの事例も出てた

Rakutenの内部ナレッジエージェントでは、Memory導入によって「first pass mistakes」が90%減ったとのこと

要するに↓

  • 前のAIがミスを記録
  • 次のAIがそれを読む
  • 同じミスを繰り返さない
  • 結果的にトークン効率も改善
  • レイテンシも下がる
  • コストも下がる

AIが経験からミスを減らすフェーズに入ってる

【6つ目】AnthropicのMemoryは「ファイルシステム」として扱う

ここが設計としてかなり面白い

Memoryを特殊な黒箱DBとして扱うのではなく、Claudeからは「ファイルシステム」に見えるようにしている

つまりClaudeは↓

  • ファイルを読む
  • ファイルを分ける
  • フォルダ構造を整理する
  • bashやgrepで検索する
  • 必要な内容を更新する

という、Claude Codeで得意な動きと同じ感覚でMemoryを管理できる

Anthropicの考え方は「モデルを縛るより、Claudeが得意な環境管理能力に任せた方が賢い」

これがかなり重要

【7つ目】Opus 4.7は「ファイル型Memory」が特に強い

Mahesいわく、先月出たClaude Opus 4.7はファイルシステム型Memoryで最先端レベルに強い

具体的には↓

  • 何を記憶すべきか判断する
  • 何は忘れていいか判断する
  • どのファイルに分けるべきか決める
  • Memoryの構造を整理する
  • bashやgrepで必要な情報を探す
  • 作業しながら記憶を更新する

つまりAIが自分で「これは経験値として残すべき」「これは一時的な情報だから不要」を判断し始めている

プロンプトで全部指示する時代から、AIが自分で知識管理する時代に移ってる

【8つ目】マルチエージェント時代にはMemory権限が必須

Anthropic社内や大企業では、すでに数百〜数千のエージェントが並列で動く世界を想定している

そうなるとMemoryにも権限管理が必要になる

例↓

  • 組織全体のナレッジ：読み取り専用
  • SLOや運用Runbook：読み取り専用
  • チーム別の作業メモ：読み書きOK
  • 進行中タスクの作業Memory：頻繁に更新OK

これがPermission Scope

AIごとに「この記憶は読めるだけ」「この記憶は更新していい」を分けられる

企業導入でめちゃくちゃ大事な部分

【9つ目】複数AIが同時に記憶を書いても壊れない仕組み

数百のAIが同じMemoryを読むだけならまだいい

問題は、同時に書き込むとき

普通にやると↓

  • AI AがMemoryを読む
  • AI BもMemoryを読む
  • AI Aが更新する
  • AI Bが古い内容を元に上書きする
  • AI Aの更新が消える

みたいな事故が起きる

AnthropicはこれをOptimistic Concurrencyで防いでいる

ざっくり言うと、更新前に「自分が読んだ内容と今の内容が同じか」をハッシュで確認する。違っていたら上書きしない

AIがチームで働くための地味だけど超重要な基盤

【10つ目】企業利用で重要な「誰が記憶を書いたか全部追える」

本番運用で一番怖いのは、AIが勝手に変な記憶を書いて、そのまま未来のAIが信じること

だからAnthropicはVersion Historyを重視している

見られるもの↓

  • いつMemoryが更新されたか
  • どのAIエージェントが更新したか
  • どのセッションで書かれたか
  • どんな差分が入ったか
  • 過去の状態に何があったか

つまりAIの記憶にも監査ログがある

これがないと企業は怖くて使えない

Memoryは便利なだけじゃなく、管理・監査・制御できる形で出してきてるのが強い

【11つ目】そして新機能「Dreaming」がヤバい

ここからが本題

AnthropicがResearch Previewで出した新機能がDreaming

Dreamingとは何か↓

複数エージェントの最近の作業ログや transcript を見て、共通する失敗・成功パターンを探し、Memoryを自動で整理・更新する非同期プロセス

つまりAIが作業してる最中ではなく、裏側でまとめて振り返りをする

人間でいうと「寝てる間に今日の経験を整理して、翌日ちょっと賢くなる」みたいな仕組み

名前がDreamingなのもそのまま

【12つ目】Dreamingでタスク完了率6倍の事例

早期テストではすでに強烈な結果が出ている

HarveyというリーガルAI系の企業が、現実的な法律タスクのベンチマークでDreamingを使ったところ、あるシナリオでタスク完了率が6倍に上がった

理由はシンプル

1体のAIだけでは気づけないパターンを、Dreamingが複数セッション横断で発見するから

  • みんな同じところで失敗してる
  • ある手順だと成功しやすい
  • この古いMemoryはもう間違ってる
  • 重複したメモが多すぎる
  • この知識は検証済みとして残せる

こういう整理を裏側で自動実行する

【13つ目】Dreamingは「作業中のAI」と別で動くのが強い

DreamingはOut-of-band つまり、タスクを実行中のAIとは別プロセスで動く

これが重要

作業中のAIに「タスクもこなして、記憶も整理して、全体傾向も見て」とやらせると負担が重い

でもDreamingなら↓

  • 作業AIは目の前のタスクに集中
  • Dreamingは裏でログを分析
  • 共通パターンを発見
  • Memoryを整理
  • 翌日のAIがその学習結果を使う

しかもホットパスに入らないので、作業中のレイテンシを増やさない

AIの現場作業と、AIの振り返りを分離している

【14つ目】デモ：障害対応AIが前の調査を引き継いだ話

デモではSREエージェントが登場

状況↓

  • dispatch serviceでP1アラート発生
  • 1体目のSREエージェントが調査開始
  • CPU使用率、トラフィック、最近のPRを確認
  • 調査結果をMemory Storeに記録

数分後、同じアラートが再発

今度は別のSREエージェントが起動する

すると最初にMemoryを見て、「この調査はすでに実施済み」「原因候補はここ」「次はここを見るべき」と分かった状態で動ける

結果、同じ調査を繰り返さずに済む

これがAIチームの引き継ぎ

【15つ目】Dreamingデモ：複数AIのログから「60秒パターン」を発見

さらにDreamingを走らせると、過去7日間の関連セッションを横断して分析した

そこでDreamingが見つけたのが↓

「dispatch latencyの問題は、上流CPUスパイクのちょうど60秒後に毎回起きている」

個別のAIは、自分のセッションしか見ていないから気づけなかった

でもDreamingは複数ログを横断して、「これ、リトライロジックが原因っぽい」とパターンを発見

さらに↓

  • 重複メモを統合
  • 古い情報を削除
  • 現在も正しいMemoryを検証
  • 未来のAIが使いやすい形に整理

完全にAI用の経験値整理システム

【16つ目】これが「AIに経験値を貯めて進化させる方法」の正体

今回Anthropicが公開した内容を3点でまとめるとこう↓

① Memory AIが作業中に学んだことを、ファイルシステム型の記憶として保存する 成功条件・失敗・環境知識・調査結果を未来のAIに引き継げる

② Multi-agent shared memory 複数AIが同じMemoryを読み書きして、チーム全体で集合知を作る 権限管理・並行制御・履歴管理まであるので企業利用できる

③ Dreaming 複数AIの作業ログを裏側で分析し、共通ミス・成功パターン・古い記憶を自動整理する 翌日のAIが昨日より賢くなる

つまりこれ、「AIを使う」から「AIを育てる」に変わる話

【17つ目】今後Claude Code勢がさらに強くなる理由

Claude Codeを10個、15個同時に回す人はすでに出てきている

ここにMemoryとDreamingが入るとどうなるか↓

  • 各Claude Codeが作業経験を残す
  • 別セッションがその経験を読む
  • 失敗パターンが共有される
  • 成功手順が蓄積される
  • Dreamingが夜間にMemoryを整理する
  • 翌日のエージェント群が前日より賢くなる

これ、普通に別ゲー

今はまだResearch Preview感あるけど、数ヶ月後に「AIエージェントは記憶を持つのが当たり前」になったら、今の使い方はかなり古く見えるはず

先に知ってるだけで実装設計が変わる内容やから、ブクマして何回か読み返す価値あるで🐼

📝 要約

🎯 AnthropicがManaged Agents向けに「Memory（ファイルシステム型の永続記憶）」と「Dreaming（複数エージェントのログを裏で横断分析しMemoryを自動整理する非同期プロセス）」を発表。Rakutenで初回ミス90%減、Harveyで法律タスク完了率6倍。「AIを使う」から「AIを育てる」へのパラダイムシフト。

📌 ポイント

Memory = AIの経験値システム（ファイルシステム型）

黒箱DBではなくClaudeから「ファイル＋bash＋grep」で操作できる構造。Opus 4.7はこの記憶管理（何を残し何を捨てるか）が最先端。プロンプトで全指示する時代から、AIが自分で知識管理する時代へ。

Dreaming = 寝てる間に賢くなる仕組み

Out-of-bandで作業中AIと別プロセス動作。複数セッション横断でパターン抽出（「60秒後に毎回障害」など個別AIには見えない傾向を発見）、重複メモ統合、古い情報削除、Memory整理を自動実行。

エンタープライズ装備が揃ってる

Permission Scope（読み取り専用/読み書きOK）、Optimistic Concurrency（同時書き込み事故防止のハッシュ確認）、Version History（誰がいつ何を更新したかの監査ログ）。企業導入に必要な「管理・監査・制御」を最初から実装。

実例の数字が強い

  • Rakuten内部ナレッジAgent：first pass mistakes 90%減
  • Harvey（リーガルAI）：タスク完了率6倍
  • SREデモ：別エージェントが前回調査を引き継いで重複調査ゼロ化

Claude Code勢の別ゲー化

10〜15個のClaude Codeを並列運用する層が、Memory+Dreamingで「夜間に賢くなるAIチーム」を持てる。実装設計レベルで前提が変わる転換点。

💡 Creative Direction Note

ゆりこさんへの活用提案

① CORINの memory/ 運用は今回の発表の先行実装そのもの ゆりこは既に ~/.claude/projects/.../memory/ で feedback / project / user / reference の4種類でファイルシステム型Memoryを運用済み。MEMORY.md インデックス + .claude/rules/critical-mistakes.md への昇格システムまである。今回のAnthropic発表は「CORINがやってきたことを公式仕様化した」と読める。

② 「Dreaming」相当を CORIN にも導入できる余地 現状は「同じやらかし2回 → rules昇格」を手動運用。Dreaming的に複数セッションログから自動でパターン抽出→memory更新する仕組みは設計可能。/done 拡張で過去N回のログを横断分析し「同じ失敗3回検出 → rules昇格提案」を半自動化できる。これCORINロードマップに乗せる価値あり。

③ AICOチーム拡大方針との相性◎ agent-teams-policy.md の「抱えきれなくなったらチーム拡大」方針と一致。新規 sub-agent（reviewer/researcher/context-updater + 将来追加）を作る時、最初から共有Memory Store（＝ memory/ 配下）を設計しておけば、各エージェントの知見がCORIN本体に逆流する集合知システムになる。

④ Optimistic Concurrency の発想を /done に取り込む 複数セッション並行運用で MEMORY.md を同時編集して上書き事故、というのは現状でも起こり得る（複数Claude Codeを並列で回した時）。/done 実行時に「自分が読んだバージョンと現在のバージョンが同じか」を確認するガードを入れると、Dreaming前段として効く。
