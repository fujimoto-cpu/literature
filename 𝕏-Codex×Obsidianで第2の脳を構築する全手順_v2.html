ここからが本題です。 【Before の限界】Claude Code × Obsidian で詰まった5つのモヤモヤ 正直に書きます。Claude Code × Obsidian で運用してきて感じていたモヤモヤは、5つありました。 モヤモヤ1: コンテキストがすぐ枯渇する これが一番大きかったです。 Vault が大きくなるにつれて、「この概念について Vault 横断で整理して」と頼むと、コンテキストウィンドウの 30% があっという間に消えていく。 実は海外の検証データでも、Claude Code は同じタスクで Codex の 3.2〜4.2倍のトークンを消費しているという結果が出ています（DataCamp / MorphLLM のベンチマーク比較）。 精度を担保するために徹底的に文脈を読み込む設計なので、品質的には正しいんです。でも Vault 全体把握型のクエリを1日に何度も投げる運用だと、コストもセッション分割の手間も無視できないサイズになってきます。 モヤモヤ2: 5時間の利用制限が運用リズムと噛み合わない Claude Code の5時間ローリング制限。これが Vault 運用と相性が悪いと感じる場面が増えました。 朝の Ingest で30%、昼の Query で20%、夕方の Lint で25%、夜の記事化で30%。体感ですが、これくらいの分配で1日が動きます。 でも記事化のフェーズで核心的なクエリを投げたタイミングで制限に当たることが、月に何度かありました。FastDoctor のチームも同じ問題を Zenn で報告していて、「5時間制限・コンテキスト30%消費・品質不安定」が Codex への並走検証を始めたきっかけだったそうです。 モヤモヤ3: モデル更新で挙動が変わる怖さ これは Claude Code というより Anthropic 側の話ですが、Opus 4.7 にアップデートされてから明らかに挙動が変わりました。 ツール呼び出しの回数が減って、推論で済ませようとする傾向が強くなった。Vault のファイルを Read せずに「このファイルにはこう書いてあるはず」と推測で答えてしまう場面が、目に見えて増えました。 エージェント生成も明らかに減りました。「3つの観点で並列調査して」と頼んでも、サブエージェントを使わず1つの推論で済ませようとする。これは記事執筆や Vault 監査のような並列作業で痛い。 モデル更新そのものは進化なんですが、運用ロジックを組み直す必要があるレベルの挙動変化が、半年に1回くらい起きるリズム。これは PKM の長期運用と相性がよくないと感じました。 モヤモヤ4: Skill Karpathy 氏が2026年4月3日に X で書いていた一文があります。 A large fraction of my recent token throughput is going less into manipulating code, and more into manipulating markdown. （最近のトークン消費は、コードをいじることより、マークダウンをいじることに使われている） これ、めちゃくちゃ象徴的でした。LLM の用途が「コード生成ツール」から「知識を整理する道具」へシフトし始めている。 ところが Claude Code は名前の通り「Code」が中心の設計で、Vault 運用は副次的な使い方。コード生成は強いんですが、マークダウンを媒体にした知識整理に最適化されているわけではない。 このズレが、Vault が大きくなるほど顕在化してきました。 【転換点】Codex に何が起きていたか — 12ヶ月の進化史 ちょうどこのタイミングで、Codex 側で大きな動きがありました。 12ヶ月で 177倍 — npm の数字が示す転換 Codex CLI の npm 月次ダウンロード数が、初期の 8.2万 から2026年3月時点で 1,453万まで伸びていました。1年で 177倍増 です。 正直、私も Codex は「OpenAI 版の Claude Code」くらいの認識で止まっていました。1年前の Codex は CLI ツールとして出始めたばかりで、機能セットも控えめだった印象です。 でも数字を見直してみると、エンタープライズ向け生成 AI 支出における Anthropic のシェアが2025年初の 10% から2026年2月で 65% まで伸びる中で、Codex 側もまったく別の軸で爆発していたという話でした。 Terminal-Bench 2.0 で立場が逆転 決定打はベンチマークでした。 Terminal-Bench 2.0 という、CLI 環境で複雑なタスクをこなす能力を測るベンチマーク。2026年2月時点では Codex（GPT-5.3-Codex）が77.3%、Claude Code（Opus 4.6）が65.4% で、12ポイントの差がついていました。 そして 2026年4月のアップデートで、GPT-5.5 搭載の Codex が 82.7%、Claude Opus 4.7 が 69.4% となり、差は 13.3ポイントに拡大。同時に「同等タスクで 72% トークン効率優位」という結果も発表されました。 「速度・自律性は Codex / 品質は Claude Code」と単純に住み分けで片付けられない場面が、CLI ベースの作業では確実に増えていました。 OpenAI 公式が「ほぼ何でもできる」と宣言 そして 2026年4月16日、OpenAI が「Codex for (almost) everything」というブログを公開しました。 Codex can now operate your computer alongside you, work with more of the tools and apps you use everyday, generate images, remember your preferences, learn from previous actions, and take on ongoing and repeatable work. （Codex はあなたのコンピュータをあなたと並んで操作し、日常的に使うツールやアプリと連携し、画像生成・記憶・過去のアクションからの学習・継続的タスクの自走を担う） 90以上のプラグイン、メモリ機能、マルチデイ自動化。CLI ツールという範疇を超えて、汎用エージェントへの格上げが宣言されました。 これは TechCrunch でも「OpenAI takes aim at Anthropic with beefed-up Codex」という見出しで取り上げられた、戦略レベルの転換でした。 開発者コミュニティでも、4月後半には「Everyone I know switched to Codex」というポストが流れ始めていました。 正直、ここまで動いているとは思っていなかったです。 【After】Codex × Obsidian — 構築した「密閉型ナレッジ工房」 ということで、1ヶ月だけ Codex × Obsidian の並走運用を始めてみました。 正直、1ヶ月では結論を出すには短いんですが、それでも明らかに違うなと感じる部分がいくつもあったので、書いていきます。 私はこのセットアップを 「密閉型ナレッジ工房」 と呼んでいます。理由は後で説明します。 5-1. Codex CLI と Obsidian Vault の連携 セットアップは想像以上に簡潔でした。 Obsidian の API キーを生成し、bin ファイルパスを確認したら、ターミナルで以下のコマンドを1行打つだけ。 codex mcp add obsidian-mcp-tools これで Codex CLI から Obsidian Vault に直接アクセスできるようになります。「今日の worklog を Obsidian に作って」「仕様をまとめて」「インシデントレポートを横断検索して」のようなプロンプトが、CLI から直接通る状態になりました。 Zenn の tenkei さんが書いていた手順そのままで動いたので、再現性も高いと思います。 5-2. ~/.codex/skills/ の自由度が違う ここが一番大きい違いでした。 Claude Code の Skill は .claude/skills/ に置きますが、ホスト側の発動ロジックが見えにくい。Codex の Skill は ~/.codex/skills/ に置く設計で、AGENTS.md でルールを Vault 内に書ける。人間と AI が同じファイルを読んでいる状態が作りやすいです。 私の場合、Claude Code と Codex の両方で使う共通スキルを _shared-ai/skills/ というディレクトリに集約していて、Codex 側は ~/.codex/skills/shared/ に junction で接続しています。 これで、Claude Code を使うときも Codex を使うときも、同じ Skill が動く。ベストプラクティス準拠チェック、引き継ぎプロンプト整形、AI×AI の2系統ファクトチェック、こういう共通スキルを両方のツールから呼び出せます。 そして Obsidian の CEO である kepano 氏が公式に公開している obsidian-skills リポジトリ（GitHub で 12,900 スター超）が Claude Code / Codex の双方に対応しているので、Skill の側からも「ホスト中立」で動かせる構造になりました。 CEO 自身がこの方向性を定義してくれたのは大きいです。 5-3. コンテキスト管理の体感差 これが一番、運用で実感した違いです。 同じ Vault に対して同じ「全ノートを横断して矛盾検出して」というクエリを投げる。Claude Code はコンテキストの30%を使って徹底的に読み込んでくれるので、品質は高い。一方で5時間制限の中で消費が早い。 Codex の方はトークン効率が高いので、同じクエリに対する消費がベースで7割程度。マルチデイで継続的に走らせる用途とすごく噛み合いました。 ただし精度は Claude Code の方が確実に上です。SWE-Bench Verified で Claude Code が 80.8%、Codex は SWE-Bench Pro で 56.8%。「徹底的に読んで答える」用途では Claude Code が頭ひとつ抜けています。 要するに、用途によって明確に使い分けが必要 ということが、1ヶ月で身に染みました。 5-4. 実際の1日の運用フロー 参考までに、1ヶ月運用してみた1日の流れを書いておきます。 朝（5〜10分） Codex の /update を実行する。daily メモを整理、inbox のノート化、コメント付きハイライトの処理、推奨読書の生成までを自動で回す。人間は「今朝この記事面白かった」のメモを raw/ に放り込むだけ。 これは Zenn の wakachikooo さんの記事で紹介されていた運用パターンを、自分の Vault に合わせてカスタマイズしたものです。AGENTS.md で指示を Vault 内に書けるので、毎日 GitHub PR で変更が自動テストされる仕組みも一緒に構築できます。 昼（深掘りクエリ） Claude Code を起動。「この概念について Vault 横断で整理して」のような 品質を最優先するクエリ はClaude Code に投げる。出力は wiki/ に保存します。 夕方（リサーチ） Codex でリサーチ系の自動化を回す。6レンズ分析（テクニカル / エコノミクス / ヒストリカル / 地政学 / コントラリアン / ファーストプリンシプル）を並列で実行。結果はすべてresearch-skill-graph/ 配下にティア付きで保存します。 夜（記事化） 記事の構成設計と執筆は Claude Code。ただし初稿のリサーチブリーフ生成は Codex に並列で走らせる。役割分担で安定するようになりました。 体感として、人間の手作業は 3分の1以下に減りました。元の Vault 運用に Codex のレイヤーが追加された、という感覚に近いです。 【Before vs After】5観点で徹底比較 ここまでの話を、表で整理しておきます。

数字だけ見ると Codex が圧勝に見えるんですが、現場で運用してみると 5観点それぞれが効く場面が違います。
速度を取りに行きたい場面 → Codex
朝の Ingest のような「素材を捌く」タスクや、「Vault に新しい構造を一気に展開する」ようなマルチデイ自動化は、Codex が圧倒的に楽でした。GPT-5.5 が 82.7% を叩き出しているターミナル系タスクは、CLI ベースの Vault 運用と相性がいい。
品質を担保したい場面 → Claude Code
逆に、「全ノート横断で矛盾検出」「核心的なクエリへの引用付き回答」のような品質クリティカルなタスクは、Claude Code の 80.8% が効きます。トークンは食うんですが、徹底的に読み込んで答える設計なので、思わぬ抜けが少ない。
コストを最適化したい場面 → Codex
ChatGPT Plus サブスクの中で Codex がほぼ追加課金なしで使える。一方で Claude Code は従量課金で、トークン消費の多さが効いてきます。Vault 全体把握型のクエリを1日10回投げる運用だと、コスト差は無視できません。
日本語の品質を取る場面 → Claude Code
これは sutero さんも Note で指摘していたんですが、Codex の日本語処理は Claude Code と比べると一段落ちます。記事執筆や日本語ドキュメントの整形は、現状 Claude Code の方が自然な日本語が出てきます。
自律的に動いてほしい場面 → Codex
OpenAI が「Codex for (almost) everything」で宣言した通り、マルチデイ自動化、メモリ機能、90以上のプラグイン連携で、CLI ツールの枠を超えた汎用エージェントとして動きます。「夜中に走らせて朝結果を確認」のような運用は、Codex の独壇場でした。
1ヶ月使ってわかった『時代の転換点』3つ
数字や機能比較とは別に、1ヶ月運用してみて思想レベルで「これは時代が動いた」と感じた瞬間が3つありました。
転換点1: AI が「補助」から「相棒」になった
これは OpenAI が「Codex for (almost) everything」で書いた一文に集約されています。
Codex can now operate your computer alongside you.
（Codex はあなたと並んで、あなたのコンピュータを操作する）
「alongside you」という表現が象徴的でした。これまでの AI ツールは「人間が依頼して、AI が応答する」という非対称な関係でした。Claude Code もそうです。
でも Codex が宣言したのは、並走関係 です。あなたと同じデスクトップを共有し、あなたが日常的に使うアプリ群と連携し、過去のアクションから学習する。
実運用でも、「夜中に Codex に Vault のリサーチを並走させて、朝起きたら結果が揃っている」という状態が成立し始めました。「自分が作業している横で、もう1人の自分が作業している」という感覚に近い。
これは思想レベルの転換だなと感じました。
転換点2: ナレッジ工房が「重い建築物」から「機動的な工房」になった
Karpathy 氏が4月3日に書いていた一文が、もう一つの象徴でした。
…going less into manipulating code, and more into manipulating markdown.
LLM の用途が「コード生成ツール」から「知識を整理する道具」へシフトし始めている。これは私自身の運用感覚と完全に一致しました。
Claude Code × Obsidian を1年運用していたとき、私の Vault は徐々に 重い建築物 になっていきました。300ノード超の Vault は、それ自体が把握・メンテナンスのコストを発生させ続ける構造でした。
Codex × Obsidian に移行してみたら、Vault が 機動的な工房 に変わりました。kepano 氏が公式に公開している obsidian-skills を Codex から呼び出すと、Vault に対する操作が「コマンド実行」レベルまで軽くなる。重い建築物を維持するのではなく、日々作り直しながら使う工房型の Vault 運用が、現実的に成立しました。
私が「密閉型ナレッジ工房」と呼んでいるのは、この感覚です。閉じた空間の中で、AI と人間が並走しながら作り直し続ける場所、という意味です。
転換点3: 統合が「コミュニティ駆動」から「公式駆動」になった
これは技術基盤の話です。
これまで Claude Code × Obsidian の統合は、コミュニティ製のプラグイン（Claudian、obsidian-claude-code-mcp など）が主役でした。完成度は高かったんですが、公式の保証はありませんでした。
ところが2026年に入ってから、Obsidian CEO の kepano 氏自身が obsidian-skills というリポジトリを公開し、12,900スター超に伸びました。これは Claude Code / Codex の 両方に対応する Agent Skills 集で、CEO が直接「公式統合の方向性」を定義した形です。
Robert Cincotta 氏は4,663ファイル・16GB の研究Vault で Obsidian CLI + Claude Code を検証し、大規模ファイル扱いの性能が 54〜70,000倍改善 したと報告しています。
つまり、これまで「コミュニティの熱量」で動いていた領域が、公式・実証・大規模対応 のフェーズに入った。Codex × Obsidian の優位性を支えているのは、Codex 単体の進化ではなく、この「公式駆動」への移行です。
ここまでが、1ヶ月使ってみて感じた『時代の転換点』3つでした。
でも Claude Code × Obsidian が完全に終わったわけではない — 棲み分け論
ここまで Codex × Obsidian の優位性を中心に書きましたが、正直に言うと 完全乗り換えは現実的ではないというのが私の1ヶ月の結論です。
実は sutero さんは Note の別記事で「Codex は Claude Code の代わりにならない」と書いていました。理由は3つ。日本語処理品質の差、両方を構築する設定コスト、Claude Code への既存投資。補完ツールとしてはOKだが、主軸切り替えには不向き という判断です。
私もこの結論にほぼ同意します。
DeNA の南場智子会長が AI 活用について語った話の中で、「Perplexity / NotebookLM / ChatGPT / Cursor を場面で使い分ける」というフレームを紹介していました。1つの最強ツールではなく、用途別の道具箱という発想。これが今の状態に一番近いです。
具体的には、こう棲み分けています。
Claude Code が向いているのは、品質クリティカルな核心クエリ（全ノート横断で矛盾検出 / 引用付き回答）、日本語ドキュメントの執筆・整形、5時間以内に集中して終わらせる作業。
Codex が向いているのは、マルチデイ自動化（夜中走らせて朝結果確認）、大量素材の Ingest と構造化、90以上のプラグインを使った外部連携、ChatGPT Plus サブスク内で済ませたいコスト最適化。
山岡敏夫さんが Note で書いていた「セカンドオピニオン」モデルも参考になります。Claude Code を主、Codex をレビュー役として並走させる設計。/codex:review（通常レビュー）、/codex:adversarial-review（厳しめチェック）、/codex:rescue（バグ調査）のように役割分担する形です。
つまり、Codex × Obsidian が来たからClaude Code × Obsidian を捨てる、という二項対立ではなく、両者を使い分けるのが新しいスタンダード ということです。
Karpathy 提唱の『コンパイラ兼司書』を Codex でどう実装するか
最後に、思想と実装の橋渡しの話を1セクション。
Karpathy 氏が提唱した「LLM を知識のコンパイラ兼司書として使う」というフレーム。これを Codex × Obsidian でどう実装するかは、運用上の最大のポイントです。
コンパイラとしての役割
raw/ に放り込まれた素材（記事・論文・YouTube 書き起こし・PDF）を、構造化された Wiki にコンパイルする役割。
Codex 側では /update のような自動化コマンドで、毎朝この処理が回ります。AGENTS.md で「raw/ に新しい素材があれば要約・概念ページ化・既存インデックスとの接続を自動生成する」と定義しておけば、人間は素材を放り込むだけ。
軽量な処理（要約・分類・タグ付け）は Codex が圧倒的に楽でした。
司書としての役割
Wiki に対して「あの概念とこの概念の関連性は？」と質問する。ここが Claude Code の出番です。
/wiki-query のようなスラッシュコマンドで、品質クリティカルな質問は Claude Code に投げる。Vault 横断の検索、引用付き回答、未解決の論点抽出。コンテキストを徹底的に使う設計が、ここで効きます。
Skill の役割分担
_shared-ai/skills/ に置く共通スキルを、両ツールから呼び出す設計が現状ベストでした。
軽量な処理は Codex、重量な処理（横断検索・矛盾検出・引用統合）は Claude Code、ベストプラクティス準拠チェックや引き継ぎプロンプト整形は両者共通。
kepano 氏の obsidian-skills を junction で両ツールに接続しておくと、CEO が公式に定義した Skill セットを Codex / Claude Code どちらからでも呼べる状態になります。
Karpathy フレームの再構築
「コンパイラ兼司書」というフレーズは、Karpathy 氏が直接の言葉で書いたものではないんですが、私はこのフレームを 「ナレッジ工房の主任技師」 と呼び替えています。コンパイラはタフな素材を組み立てる現場仕事、司書は問いに答える知的仕事。両方を1人で担当する主任技師像のほうが、運用イメージに合っていました。
このイメージで Vault を運用すると、何をCodex に頼んで何を Claude Code に頼むか の境界が、ぐっと明確になります。
まとめ — Before/After で「卒業した3つのこと」
1年運用してきて、ここ1ヶ月で 卒業した ことが3つあります。
  1. 「単一AI依存」を卒業する Claude Code 一本足から、Codex との並走へ。1つの最強ツールに依存するのではなく、用途別の道具箱に持ち替える。
  2. 「重い建築物的Vault運用」を卒業する 300ノード超の Vault を維持する重さから、機動的に作り直し続ける工房型へ。「密閉型ナレッジ工房」という運用イメージに移行する。
  3. 「コミュニティ頼みの統合」を卒業する Claudian や obsidian-claude-code-mcp に依存する状態から、Obsidian CEO 公式の obsidian-skills を起点にした 公式駆動の Vault 運用 へ。 「Claude Code × Obsidian は時代遅れだ」という二項対立で語るのではなく、ツールの組み合わせを再設計する時代に入ったというのが、この1ヶ月の結論です。 明日からの運用を見直すきっかけになれば、嬉しいです。
