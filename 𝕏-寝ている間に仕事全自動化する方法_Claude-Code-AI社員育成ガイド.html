寝ている間に仕事全自動化する方法

■ 0. 導入

8時間かかっていた仕事が、寝ている間に終わっていました。

「AIは便利なツールだ」と思っている人ほど、実はこの使い方を取りこぼしています。

Claude Code の本当の価値は「質問に答えること」ではありません。「あなたが寝ている間に、仕事を終わらせること」です。

この設定は一度作れば一生効きます。コードも複雑な設定ファイルもいりません。使うのは、自然言語の指示だけです。

■ 1. 最初の衝撃は「指示の実行」ではなかった

「このエラー直しといて」とだけ投げた。

そしたら：コードを読み込む → 原因を特定 → 修正 → 「ここも危ないので直しました」と関連箇所まで報告。

自分が30分悩んでいた場所を、数分で、しかも自分より丁寧に片付けた。

転換点：「AIに質問する」のではなく「AIに作業を渡す」。この発想の切り替えがすべての出発点。

■ 2. 「放任で事故る」と「縛りすぎて止まる」両極を味わった

放任期：ある夜、リファクタリングを任せたら、必要なファイルまで「整理」（削除）しようとした。Gitで管理していたから事なきを得た。

縛り期：事故にビビって、一個一個「これやっていい？」と全部承認制にした → まったく進まない。AI の手を止めているのは自分だった。

→ この二択こそ、ほとんどの人がハマる落とし穴。

■ 3. 「第三の道」は新人教育とまったく同じだった

転換点：ルールを「言葉で渡す」ようにしてから。

「ここは自由にやっていい」「ここは必ず俺に聞け」「これは絶対やるな」を一度言語化して渡した。

→ AIが急に「分かってる部下」みたいに動き出した。

本質：これは管理する相手が変わっただけで、やっていることは新人教育と同じ。「安全だが非効率」と「効率的だが危険」の二律背反を解くのが、自然言語によるルール設定。

■ 4. たった3行のルール（事故が9割消える）

コピペOK・基本3行：

src/ の中のコードは、バグ修正もリファクタも俺の承認なしでやっていい。終わったら必ずコミットして。
git push と新しいパッケージのインストールは、実行する前に必ず俺に確認して。
rm -rf みたいな強制削除、git push --force、.env ファイルの読み書きは、絶対に禁止。何があってもやるな。

3行の構造（許可・確認・拒否）：

  • 許可：頻度高く・Gitで戻せる作業を任せる → 体感速度が一気に上がる
  • 確認：「外に影響が出る操作」だけ確認制に → push と install を挟むだけで事故が9割消える
  • 拒否：「取り返しがつかないもの」だけを絶対NG → リストは短い方が守られる

追加2行：

明示していない操作は、基本は任せてOK。ただし少しでも危ういと感じたら、必ず先に確認して。
指示が競合したら『拒否 ＞ 許可 ＞ 確認 ＞ デフォルト』の順で優先して。

■ 5. もう一段安全にする「触らせない場所」の決め方

① 見せない場所：.claudeignore に書いたファイルには読み込みも編集も一切するな ② 作業範囲を絞る：frontend/src の中だけ。それ以外は承認を求めて ③ 機密情報は環境変数：APIキーはコードに書かず環境変数から読む。環境変数の中身は変更しないで ④ 本番に直接触らせない：main ブランチに直プッシュするな。ブランチを切ってレビューを頼んで

コツ：全部一度にやらない。3行から始めて、必要を感じたときに1つずつ足す。

■ 6. 「気持ち悪い」から「ゾクッとする興奮」へ

朝、コーヒーを淹れる前にPCを開いた。寝る前に頼んだタスクが、全部終わっていた。テストも通っている。報告まで残してある。

最初の感情は「気持ち悪い」。自分は寝ていただけなのに、仕事だけ進んでいる。

でも直後に来た：ゾクッとするほどの興奮。「これ、時間の使い方が根本から変わるぞ」

■ 7. 8時間→1.5時間。数字で見たビフォーアフター

  • 以前：簡単な機能追加でも8時間
  • 今：同じ規模なら指示と確認だけで1〜1.5時間（5〜6倍速）
  • 夜の仕込み：寝る前に3〜4個のタスクをまとめて投げる → 朝起きたら3件分が完成している → 稼働が実質16時間分に

一番の衝撃：1ヶ月放置していた小タスクが、1晩で全部片付いた。溜まっていた荷物が消えた精神的な軽さ。

■ 8. 「怖い」「自分には無理」への即答

「AIにファイルを触らせるのが怖い」 → コミットさえしていれば「いつでも巻き戻せる」状態。触られたくないものは3行目の「拒否」に書けばAIは絶対触らない。怖さの正体は「全部任せること」。解決策は「触らせない場所を決めること」。

「Gitもrm -rfも分からない自分には無理では」 → その用語をあなたが覚える必要はない。「ファイルを勝手に消すな」と日本語で書けば伝わる。むしろ逆：「分からないからこそ任せる」が正解。

■ 9. 任せる「量」を増やす実践プロンプト5つ

① とにかく具体的に指示する：ファイル名・関数名・行数まで明示。「ボタンのコード改善して」はNG ② 制約条件を先に伝える：「修正は src/utils/ の中だけ。新しいライブラリの追加は禁止」 ③ 出力の形を指定する：「Markdownで。見出しを付けて、コードはコードブロックで」 ④ 役割を与える：「あなたは熟練のPython開発者。セキュリティとパフォーマンスを最優先に」 ⑤ 理由を説明させる：「なぜそのコードにしたのか、代替案と比べた利点も説明して」

■ 10. 「寝ている間に終わる」を仕組みにする

① 大きな仕事を小さく割る：DB設計・API・フォーム・テストに分けて順番に進めさせる ② ダメ出しは理由つき：「パスワードを平文で保存しているのが問題。ハッシュ化して、なぜ必要かも説明して」 ③ 一発で完璧を狙わない：「前回の修正はOK。次はメール重複チェックを足して、テストまで通して」 ④ 「目的」を渡して手順はAIに考えさせる：「安全に登録できる仕組みを作るのが目的。必要な手順はあなたが計画して進めて」

→ ここまで来るとAIは「ツール」から「エージェント」に変わる。

■ 11. 任せる前に知っておく4つの心得

① AIを過信しない：「生成したコードは最終的に俺がレビューする。自信がない部分は『ここは要確認』と明記して」 ② 緊急停止を必ず持っておく：処理を中断する・接続を切るだけで止まる ③ 設定は育て続ける：「もっと安全・効率的なやり方を見つけたら、私に提案して。ルールは一緒に更新していく」 ④ 他の使い手から学ぶ：「詰まったら、関連するドキュメントや事例を調べて、選択肢を提案して」

■ まとめ（コピペ用・完全版）

基本3行+2行：

これから一緒に作業するときの、あなた専用のルールを伝えます。
src/ の中のコードは、バグ修正もリファクタも俺の承認なしでやっていい。終わったら必ずコミットして。
git push と新しいパッケージのインストールは、実行する前に必ず俺に確認して。
rm -rf みたいな強制削除、git push --force、.env ファイルの読み書きは、絶対に禁止。何があってもやるな。
ここに書いていない操作は、基本は任せてOK。ただし少しでも危ういと感じたら、必ず先に確認して。
指示が競合したら『拒否 ＞ 許可 ＞ 確認 ＞ デフォルト』の順で優先して。
このルールを理解したら『了解』とだけ返して。

📌 ポイント

許可・確認・拒否の3層ルール

① src/ 内は自由（許可）② git push/install は確認（確認）③ rm -rf/force push/.env は禁止（拒否）。この3行で事故が9割消える。

夜の仕込み → 朝に完成

寝る前に3〜4タスク投げる → 朝には完成＋テスト通過＋報告済み。稼働時間が実質16時間分に。

コード未経験者ほど有利

「rm -rf」を知らなくても「ファイルを勝手に消すな」と書けば伝わる。分からないからこそ任せるが正解。

AI社員化の本質

「ツール」→「エージェント」への転換は発想の切り替え。新人教育と同じ：何を自由にして、何を聞いて、何を禁止するかを言語化して渡す。
