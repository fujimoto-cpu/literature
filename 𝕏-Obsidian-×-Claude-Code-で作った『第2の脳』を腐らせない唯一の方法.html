Obsidian × Claude Code で作った『第2の脳』を腐らせない唯一の方法

第2の脳は作れた。でも実は、それ１か月で使い物にならなくなります。その詰む理由とそれを解決する最強の設計方法をすべてこの記事で徹底解説します。 オープンソースの第2の脳プラグインを入れて、CLAUDE.mdをコピペして、スキルをいくつか有効にする。 ここまでなら30分で終わる。 ただ、ここで「動いた感」だけ手に入れて、止まる人がほとんどです。 問題は1ヶ月後に来る。 ノートが溜まる。スキルが増える。hookが鳴る。 でも、頭のなかは前より散らかっている。 「賢くなったはずなのに、使いこなせてる感がない」状態に着地します。 この記事では、その壁の正体と、抜け方を全部書きます。 100億字スケールで運用しながら組み直してきた4レイヤー設計の話。 設計判断のなぜまで含めて、ぜんぶ置いていきます。 １. テンプレ運用で見えた壁 — 1ヶ月で気づいた3つの頭打ち 最初のうちは、テンプレで十分動きます。 claude-obsidianを入れる。/saveで会話をWiki化する。/autoresearchを回す。 入れた当日は感動するんです。「これが第2の脳か」って。 でも、1ヶ月続けると、3つの頭打ちが順番に来ます。 頭打ち①: 期待通りに動かない瞬間が増える テンプレ運用の前提は「みんな同じように使う」です。 でも実際は、書きたい記事も扱う領域も語り口も人それぞれ違う。 汎用テンプレを汎用のまま使うと、微妙にズレた成果物が量産されます。 「会話を保存して」と言って出てくるWikiページが、毎回同じ構造で書かれる。 最初は便利でも、3週目には「自分のリズムと違う」と感じ始めます。 頭打ち②: カスタマイズしようとすると詰まる 「じゃあ自分用に書き換えよう」と思って中身を開くと、ここで詰まる人が多い。 CLAUDE.mdが何百行もある。スキル定義もネストが深い。hookは依存関係がよく分からない。 公開リポジトリには500行を超えるCLAUDE.mdも普通に転がっています。 ある検証記事の実測では、650行を超えると約70%のルールが無視されるという報告も出ていました。 書いてある量と効いている量は、まったく別の話だったんです。 「とりあえず長く書いておけば賢くなる」は、わりと幻想でした。 頭打ち③: ツール同士が競合する 第2の脳系のプラグインは、似た領域に複数の選択肢があります。 Smart Connections、Obsidian Copilot、claude-obsidian、Claudian。 公開Issueを覗くと、「path設定が通らない」「環境依存でエラーが出る」「PostToolUse hookが無音で失敗する」みたいな報告が普通に並んでいます。 入れる順番、組み合わせ、OS、Vault規模。 少しでも条件が違うと、テンプレ通りには動きません。 共通項は「テンプレは初動には効くが、深掘りに耐えない」 3つの頭打ちに共通するのは、テンプレが「初動最適化」の道具だという事実です。 5分で始められる。動いた感がある。スクショ映えする。 ここまではいい。 でも「自分の脳と本当に統合する」フェーズに入ると、設計を変えないと進めません。 ここから先が、4レイヤー設計の話です。 ２. 「第2の脳」の本質 — JARVISじゃなくて思考パートナー そもそも、第2の脳ってなんでしょうか。 JARVISのような完全自律エージェント？ 朝起きたら勝手にスケジュールを最適化して、メールを返して、要点だけ報告してくれる存在？ このイメージで設計すると、まず壊れます。 完全自律は、いまの言語モデルには無理だという事実が前提です。 文脈は腐るし、長時間セッションは崩れるし、ルールは100%守られない。 それでも「賢いシステム」を設計したいなら、別の定義が必要になります。 永続的に複利で育つ「成果物」として定義する ある研究者が提唱したLLM Wikiパターンという考え方があります。 雑に要約すると、こういう発想です。 知識を毎回ゼロから作るのではなく、永続的に複利で蓄積する成果物として持つ。 毎回問い合わせて再導出する従来のRAG的な発想ではなく、一度コンパイルされて最新に保たれるWikiを育てる。 LLMが、そのWikiを漸進的に組み立ててメンテし続ける。 これ、しっくりくる設計思想です。 ただし、しっくりきたあとに気づくことがあります。 「永続的に複利で育つ」と言うと美しいけど、実装すると毎日メンテが要る。 LLMが勝手に育ててくれるわけじゃない。 育つ条件は、人間が下層を腐らせないこと。 第2の脳は、AIそのものでも、ノートアプリでもない。 「AIと一緒に、時間をかけて育てていく成果物」だと考えると、設計の方向が変わります。 だから「ツール紹介」じゃなく「設計判断」の話になる 成果物を育てる以上、入れ物だけあっても意味がない。 何を、どこに、どんなルールで、どう自動化するか。 この設計判断が、第2の脳の質を決めます。 つまりこの記事は、ツール紹介ではないんです。 「自分の脳と統合できる成果物を育てるには、どう層を組むか」の話です。 ここからの4セクションが、その4レイヤーになります。 ３. 4レイヤー設計の全体像 — なぜこの順番なのか 最初に全体像を置いておきます。 Layer 4 ─ 協調層 sub-agents / multi-agent 文脈を分離して設計者と実装者を分ける ↑ Layer 3 ─ 機能層 commands / skills 再利用可能な業務単位として切り出す ↑ Layer 2 ─ 自動化層 hooks 「忘れる」「サボる」を物理ブロック ↑ Layer 1 ─ コンテキスト層 CLAUDE.md / rules/ 「司令塔」と「状況別ルール」を分離 下から順に積む。 順番が決まっているのには理由があります。 なぜLayer 1から積むのか Layer 2の自動化（hook）は、Layer 1のルールが整っていないと暴発します。 Layer 3のスキルは、Layer 1のコンテキスト設計とLayer 2のhookで「呼ぶ条件」が決まる。 Layer 4の協調は、Layer 3が安定してないと、エージェントごとに別々の挙動を取り始める。 つまり下層が腐ると、上層が機能不全になる。 逆も成り立ちます。 下層が整っていれば、上層を増やしても複利で効いてくる。 テンプレ運用が止まる理由を、この階層で説明できる テンプレで詰まる人の典型パターンが、この階層で見ると分かりやすい。 入れた最初は、Layer 3（スキル）の便利さで動いた感がある。 でも、Layer 1がコピペのまま放置されているので、自分の領域に合わない。 Layer 2のhookは、テンプレが想定する場面でしか発火しないので、自分の運用には噛まない。 Layer 4の協調は、そもそも入れていない人がほとんど。 結果、「Layer 3だけが浮いている状態」になります。 これが「動いた感はあるのに、使いこなせてる感がない」の正体です。 ここから、各レイヤーを深掘りします。 実際に組み直してきた、設計判断の話です。 ４. Layer 1 — コンテキスト層 / CLAUDE.mdを「司令塔」にする 第2の脳の土台は、CLAUDE.mdです。 ここが腐ると、上の3層が全部ズレます。 最初にやってしまいがちなのが、「全部CLAUDE.mdに書く」運用です。 自分の役割、好み、口調、プロジェクト一覧、過去のミス、ファイル命名規則、禁止表現……。 書こうと思えばいくらでも書ける。 ただ、これが最大の罠です。 200行以下を目指す、というのが公式ライン Anthropicの公式ドキュメントには、はっきり書いてあります。 CLAUDE.md is loaded into context at session start. Skills load only when invoked. Aim for under 200 lines and move specialized instructions into Skills. 意訳すると、「CLAUDE.mdはセッション開始時に毎回読まれる。専門指示はスキルに移して、200行以下を目指せ」。 毎ターン読まれる、という性質が重要です。 500行書けば、毎ターン500行読まれる。 1,000行なら毎ターン1,000行。 ここにゴーストトークンが積まれていきます。 認知負荷の上限は150〜200命令 ある検証記事には、もっとシビアな指摘もありました。 LLMの指示追従能力は、150〜200命令で上限に達する。500行のCLAUDE.mdは既に過負荷の領域。 500行書いた時点で、書いた本人が「効いている」と感じていても、実際は約7割が無視されているという事実です。 これ、自分でやっても再現できました。 CLAUDE.mdが半年で12行→520行に膨らんだ時期があったんです。 気づいたきっかけは、自分で書いた禁止事項をClaudeが3日連続で踏んだこと。 「これ書いたよね？」と確認したら、ファイルにはちゃんと残っていました。 でも遠くなりすぎて、もう効いていなかった。 長く書くほど、書いた本人すら忘れる。 短いCLAUDE.mdに「ルーティングだけ」書いて、状況別の詳細を別ファイルにすると、忘れません。 差は劇的でした。 ルーティングディレクトリ化、というやり方 そこで、CLAUDE.mdを「司令塔」として再設計します。 中身は、ほぼこの3つだけ。 自分が誰で、何をしているか（10行程度） どんな環境で動いているか（OS、シェル、ワークスペース、5行程度） 状況別にどのルールファイルを参照するか（IF-THEN形式、20〜30行） 具体的には、こんな構造です。

Context Routing

  • ファイル操作・プラグイン追加 → rules/file-organization.md
  • 助言・フィードバック → rules/advisor-stance.md
  • コンパクション後・コンテキスト管理 → rules/context-management.md
  • ルール肥大化・定期整理 → rules/maintenance.md
  • ミスからの再発防止 → rules/mistakes.md CLAUDE.mdは「目次」になる。 詳細はrules/配下のファイルに切り出す。 該当する場面が来たときだけ、Claudeがそのファイルを読み込む。 この設計に変えてから、初期コンテキストが70%程度減りました。 しかも、ルールがちゃんと効くようになる。 短くて目次的だから、毎ターン読まれても負荷にならない。 詳細は必要なときだけ呼ばれるから、無視されない。 rules/ への分離基準 何を切り出すか、迷うところです。 判断基準として使っているのは、こうです。 その内容は「毎回参照する必要があるか」「ある状況でしか使わないか」のどちらか。 毎回必要なら、CLAUDE.mdに残す（自分の役割、環境、ルーティング目次）。 ある状況でしか使わないなら、rules/に切り出す（ファイル操作の詳細、ミス記録、プラグイン構造の話、文体ガイドなど）。 この判断軸を持っておくだけで、CLAUDE.mdは肥大化しません。 罠: 切り出した先のルールも肥大化する これ、実際にハマりました。 CLAUDE.mdは200行に収めた。 でも切り出したrules/mistakes.mdが、3ヶ月で100kbを超えたんです。 セッション中に該当場面が来ると、Claudeはこのファイルを読みに行く。 毎回100kb読むと、それはそれで重い。 対策は2つ。 ひとつは、「履歴アーカイブとアクティブルールを分離する」。 過去のミス事例を全部mistakes.mdに置くのではなく、再発防止ルールだけ残して、個別の事例はmistakes-archive.mdに逃がす。 もうひとつは、月1回の整理日を持つこと。 ルールが20を超えたら、矛盾チェック、重複統合、解決済みの削除をやる。 これを「スパデー」と呼んでいます。 CLAUDE.md側のルーティングを叩いて、/spa-dayのような自分用コマンドを作っておくと、定期整理が習慣になる。 このレイヤーで読者がやるべきこと このセクションをまとめると、最初の一手はシンプルです。 いまのCLAUDE.mdを開く。 行数を数える。 200行を超えていたら、まずルーティングディレクトリ化をやる。 切り出したrules/は1ファイル200行を上限の目安にする。 これだけで、上に積む3層の効きが、劇的に変わります。 ５. Layer 2 — 自動化層 / hookで「忘れる」を物理ブロックする Layer 1がきれいになったら、次はLayer 2です。 ここがいちばん「複利が効く」レイヤーです。 ただし、いちばん設計をミスると爆発するレイヤーでもあります。 hookの本質は「ルールを物理的に強制する」こと Anthropic公式のhooksドキュメントには、こう書かれています。 Hooks are user-defined shell commands that execute automatically at specific points in Claude Code’s lifecycle. ライフサイクル上のイベントに反応して、シェルコマンドを自動実行する。 これだけ聞くと地味なんですが、効果はすごいです。 たとえば「Write/Edit直後にReadさせる」というルールを、文字で書いてもClaudeは70%くらい忘れます。 ところがhookで「Write後にReadしないと次のツール呼び出しを物理的にブロックする」ようにすると、100%守られるようになる。 ルールを書く、から、ルールを物理的に強制する、への移行です。 ミス→記録→再発防止の複利ループ Claude Codeのリードエンジニアが公開している運用パターンに、こういう一文があります。 Anytime we see Claude do something incorrectly we add it to the CLAUDE.md, so Claude knows not to do it next time. 意訳すると、「Claudeが何か間違えたら、その内容をCLAUDE.mdに追記する。次から同じミスをしないように」。 これ、Compounding Engineeringと呼ばれる発想です。 設計者が頭で覚えているルールではなく、ファイルに記録して永続化する。 ただし、書いてある人がやらない部分が1つある。 追記しても、書いた本人が翌日にはルールを忘れるんです。 人間の手で記録するだけだと、再発が止まらない。 だから、hookで自動化すると複利が効きます。 具体的には、こういう流れです。 セッション終了時に、Stop hookが発火する。 「今回のセッションでミスはあったか？」をClaudeに振り返らせる。 ミスがあれば、mistakes.mdに追記する。 次のセッションで同じ場面が来ると、ルールが効いて、同じミスを繰り返さない。 人間の手で記録しなくていい。 寝てる間にも、第2の脳が育つ仕組みです。 hook肥大化の罠 — 起動が遅くなる現象 ここに、典型的な落とし穴があります。 hookを増やせば増やすほど、起動が遅くなる。 公開Issueに、こんな実測値が出ていました。 クリーンな環境では起動が4.9秒。hookを11個 + 9つのライフサイクル設定を入れると18.2秒。 4倍近く遅くなる。 自分も、これに近い状態に一度ハマりました。 hookを20個近く積んでいたあるとき、立ち上げに30秒近くかかっていることに気づいた。 最初は気づかない。毎日触るから、慣れて遅さが見えなくなる。 別の環境を1日触ったあと、自分のClaude Codeに戻ったら、明らかに重い。 Claude Codeの体験の核は速さなのに、自分でそれを潰していたわけです。 便利だからとhookを次々入れていると、立ち上げのたびに18秒待つことになる。 ここが鈍ると、使う頻度が落ちます。 設計指針: hookは「忘れちゃダメなこと」だけに絞る 絞り方は、判断基準を1つ決めると安定します。 その挙動を「hookで強制しないと忘れるか」「Claudeが自然にやってくれるか」。 Claudeが自然にやることは、わざわざhookで強制しない。 逆に、絶対忘れちゃダメなこと（Write後のRead、ミス記録、危険コマンドのブロックなど）は、hookで物理的に止める。 具体的には、こういう優先度になります。 最優先は「壊滅的ミスの予防」(rm -rf系のブロック、強制push防止、機密ファイル読み取り防止)。 次が「品質に直結する強制」(Write/Edit後のRead、文字数下限チェック、ミス追記)。 その下が「便利系」(セッション開始時のVault状況サマリー、自動コミット、通知)。 便利系は便利ですが、hookじゃなくてコマンドでもいいことが多い。 「都度起動する便利機能」は、Layer 3のskillsに置く方が適切です。 hookに置くべきなのは「黙っていても発火する必要があるもの」だけ。 もうひとつの罠: hookが無音で失敗する 公開ナレッジには、もうひとつ嫌な事例があります。 PostToolUse hooksが無音で失敗する。「自動コミットを設定したはずなのに、何も起きない」。 これ、自分も経験しました。 hookが鳴らない。エラーログも出ない。 設定ファイルを見直しても合っているように見える。 原因は、シェルのパス問題、改行コード、引数の渡し方、bash vs Node.js、いろいろある。 対策はシンプルで、hookには必ずログ出力を仕込むこと。 発火しても、しなくても、ログにイベントを残す。 無音失敗を見逃さないだけで、デバッグ時間がだいぶ減ります。 このレイヤーで読者がやるべきこと hookは「書いて強制する」道具です。 最初に入れるべきhookは、3つに絞っていい。 ひとつ目が、Write/Edit直後にReadを強制するhook。 ふたつ目が、危険なBashコマンドをブロックするhook。 3つ目が、セッション終了時にミスを振り返ってmistakes.mdに追記するhook。 ここから始めて、月に1〜2個ずつ追加する。 増やしすぎたら、起動時間を測って、効果のないhookは外す。 「書いて強制する」は強力ですが、強力だからこそ慎重に積む必要があります。 ６. Layer 3 — 機能層 / commandsとskillsの使い分け Layer 1とLayer 2が整ったら、ようやくLayer 3が活きてきます。 ここは「再利用可能な業務単位」を切り出すレイヤーです。 commandsとskillsの違いを最初に押さえる commandsとskillsは、似ているようで役割が違います。 commandsは、ユーザーが/コマンド名で明示的に呼ぶもの。 「いま、これをやって」と能動的に呼び出す。 メリットは、確実に発火すること。 デメリットは、コマンド名を覚えていないと使えないこと。 skillsは、Claudeが自動判断で起動するもの。 スキル定義に「こういう場面で使え」というdescriptionを書いておくと、その場面が来たときにClaudeが勝手に呼ぶ。 メリットは、覚えていなくても発火すること。 デメリットは、descriptionが弱いと発火しないこと。 両者を混ぜて使うのが正解です。 使い分けの基準 ある業務を新しく自動化したいとき、判断軸はこうです。 「ユーザーが毎回意識して呼びたいか」「条件が揃ったら勝手にやってほしいか」。 前者ならcommand。 後者ならskill。 たとえば、記事執筆はcommandの方が向きます。 「いまから記事書く」と明示的に宣言したいから。 逆に、コードを書いたときの整形・型チェックは、skillの方が向きます。 毎回「整形して」と言いたくないから。 skill肥大化の罠 — 「30個入れて使ってない」状態 skillはdescriptionで自動発動するので、調子に乗ると増えます。 Anthropic公式のプラグインエコシステムだけでも、キュレーション済み55+ + コミュニティ72+のプラグインが公開されています。 便利そうなのを片っ端から入れると、すぐに数十個になる。 ここで起きるのが「入れてるのに使ってない」状態です。 なぜ使われないかというと、descriptionが他のskillと被っていて、Claudeが「どれを呼ぶべきか」迷う。 迷った結果、素朴な応答を返すか、間違ったskillを起動する。 skillを30個入れた人が、結局5個しか使っていない、というのは普通の話です。 棚卸しの方法はシンプルで、SKILL.mdを流し読みして、最近1ヶ月で「自動発動した記憶があるか」を1個ずつ判定するだけ。 記憶にないものは、descriptionが弱いか、用途が他とブレているか、のどっちかでした。 そういうskillを片っ端から外して、残ったものだけを「機能層」として扱います。 「100%動かない自動化は、自動化ではない」 Claude CodeのProductチームに、ある原則があります。 If an automation doesn’t work 100% of the time, it’s not really an automation. 90%動くskillは、自動化じゃないんです。 これ、最初は「厳しすぎでは」と思ってました。 でも、自分で30個近くskillを入れて、実働4個だった事実を見たら納得した。 自動化の定義から外れたものを、自動化と呼んでいたから増えたんです。 なぜかというと、人間が「これ動くかな？」と毎回チェックする必要が出てくるから。 チェックするコストを払うくらいなら、最初から自分でやった方が早い。 自動化の本質は「考えなくていい状態」を作ること。 90%だと、結局考えてしまうので、自動化の意味がない。 この基準でskillを棚卸しすると、ほとんどのskillが落ちます。 残ったskillだけが、本当の意味で第2の脳の機能になる。 skillの設計指針 設計の整理は、3つの観点で絞っていきます。 ひとつ目は、descriptionを具体的なトリガーフレーズで書くこと。 「This skill should be used when the user asks to …」のあとに、実際の発言を3〜5個並べる。 抽象的に書くと発火しないし、具体的に書くと他とぶつからない。 ふたつ目は、そのskillが100%動く境界を明示すること。 「Aの場合は対応、Bの場合はskip」と明確に切り分ける。 万能skillを作ろうとすると、100%は絶対に達成できない。 3つ目は、skillの中で再帰的にskillを呼ばない。 呼ばれた先でまた別のskillが発火する設計は、文脈が壊れます。 skillは1階層に留めるのが安全です。 スキル定義の中身を、別ファイルに分ける skillが肥大化する別のパターンが、SKILL.mdに全部書き込むことです。 定義、手順、参考データ、過去の修正パターン。 これを一枚にまとめると、毎回呼ばれるたびに全部読まれる。 参考データや過去のパターンは、references/配下の別ファイルに切り出す。 SKILL.mdからは、必要なときだけそのファイルを参照する。 CLAUDE.md / rules/ の関係と同じ構造です。 このレイヤーで読者がやるべきこと skillsをこれから増やすなら、最初の1個は「自分の言葉で記事を書く」「自分のリズムで会話を保存する」みたいな、自分専用の業務を選んでください。 汎用テンプレを大量に入れる前に、自分の業務を1つだけ自動化する。 そのskillを使い倒して、本当に100%動くまで磨く。 そこから、月に1〜2個ずつ増やしていく。 増えてきたら、四半期に1度、棚卸しをやる。 「直近1ヶ月で1度も呼ばれていないskill」は、外す。 これだけで、機能層は腐りません。 ７. Layer 4 — 協調層 / 文脈を分離して設計者と実装者を分ける 最後のレイヤーが、いちばん難易度が高い領域です。 ここを間違えると、せっかく組んだ下3層がまとめて崩壊します。 sub-agentの本質: 文脈を分離する Claude Codeには、メインのClaudeから別のエージェントを呼ぶ機能があります。 sub-agent、もしくはサブエージェントと呼ばれるものです。 最初は「並列処理で速くする」道具に見える。 実際そうなんですが、本質はもっと別のところにあります。 本質は、「メインの文脈を汚さずに、別タスクを走らせる」こと。 たとえば、記事執筆のセッション中に、過去ノート500件をリサーチしたい。 メインClaudeが直接読むと、500件分の本文が文脈に入ってきて、執筆中の集中力が落ちる。 sub-agentを呼んで、そっちで500件読ませて、要約だけ返してもらう。 メインClaudeの文脈は、要約500字だけ増える。 これが文脈の経済です。 メインの文脈を、いちばん大事な作業のためだけに使う。 設計者と実装者を分けるパターン もうひとつ、強力なパターンがあります。 メインClaudeを設計者、sub-agentを実装者として役割分離する。 メインで方針を決めて、実装はsub-agentに渡す。 sub-agentで作ったものを、メインがレビューする。 この分離が効く理由は、3つあります。 ひとつ目が、思考の重さが違うから。 設計は重く、実装は軽い。両方を1つのClaudeにやらせると、設計の重さに引きずられて実装が遅くなる。 ふたつ目が、コンテキストの汚染を防げるから。 実装者のsub-agentは、実装に必要な情報だけ受け取る。設計の議論は持たない。だから判断がブレない。 3つ目が、モデルの使い分けができるから。 設計はxhighの推論モデル、実装は中程度のモデル、こういうコスト最適化ができる。 ある公開記事には、こういう実例も紹介されていました。 高推論モデルのsub-agentsを、別系統の実装モデル一本に置き換えたら、品質が劇的に上がった。 設計者×実装者という構造を、モデルレベルで分けたわけです。 罠: agentを増やしすぎると壊れる ここが、協調層の核心的な落とし穴です。 sub-agentが便利だからといって、無制限に増やすと壊れます。 公開ナレッジに、こんな事例がありました。 AI社員を40体作って、1ヶ月で全廃棄した。 理由を要約するとこうです。 context rot（10万トークンを超えたあたりから出力の一貫性が劣化する現象）が頻発する。 compaction崩壊（自動圧縮で「3人が消えて2人が重複する」のような事故）が起きる。 テキストルールは絶対じゃないので、agentによって挙動がブレる。 1週間で再現性が落ちて、2週間で原因不明、1ヶ月で運用終了。 これ読んだとき、自分は他人事に思えませんでした。 似たことを、もっと小規模でやっていたからです。 3〜5体で十分動くものを、なぜ40体に増やしたくなるのか。 便利だから、ではないんです。 「もっと自動化したい」という設計者の欲が暴走するから、増える。 40体のagentを並列で動かす設計は、人間が把握できる規模を超えるという事実があります。 context rotの閾値はソースで違う context rotが起き始める閾値は、ソースによって幅があります。 Anthropic社員の発言ベースだと、30〜40万トークンから観察可能。 実運用ベースの報告だと、10万トークンを超えたあたりから劣化を体感する人もいる。 自分の体感は、後者の方に近いです。 10万トークン超えたセッションは、明らかに「あれ、いまの判断おかしい」が増える。 ベンチマークの数字より、自分の実運用の体感を信じる方が安全です。 sub-agentの設計指針 協調層を組むなら、設計指針はこうです。 ひとつ目は、agentの数を最大3〜5つに絞る。 設計者、実装者、リサーチャー、レビュアー。これくらいで十分です。 ふたつ目は、役割を明確に分離する。 「実装もできるし設計もできる」みたいな万能agentを作らない。 3つ目は、コンテキスト共有を最小化する。 agent間で同じ情報を引き渡しすぎると、文脈が増えていく。 「タスク開始時に必要な情報だけ渡す」「結果は要約だけ返す」を徹底する。 4つ目は、長時間の並列を避ける。 3時間以上並列で動かすと、compaction崩壊が起きやすい。 タスクは1〜2時間で区切る。 このレイヤーで読者がやるべきこと 協調層は、Layer 1〜3が安定してから手を出してください。 下層が腐っているのに上層を増やすと、agentごとに違う挙動を取り始めます。 最初に組むのは、設計者×実装者の2体構成でいい。 メインClaudeが設計、sub-agentが実装。 これだけでも、メインの文脈はかなり守られます。 自分も2体構成でしばらく回したあと、欲を出して8体まで増やしたことがあります。 1週間で、文脈がブレ始めました。 設計者役のClaudeが、実装者役のsub-agentと同じことを言い出す。 役割分離が崩れた瞬間、複数体を動かす意味は消える。 8体を3体に戻したら、品質が一気に戻りました。 慣れたら、リサーチャーやレビュアーを追加する。 40体は要らないです。 3〜5体で、第2の脳の協調層は十分に機能します。 ８. Before / After — 4レイヤー導入で何が変わるか 各レイヤーの設計判断を見てきました。 ここで一度、テンプレ運用と4レイヤー設計を並べてみます。 レイヤー | テンプレ運用（Before） | 4レイヤー設計（After） Layer 1 | CLAUDE.mdに何でも書き込む / 500行以上で7割無視 | ルーティング20〜30行 + rules/に切り出し / 70%のトークン削減 Layer 2 | 便利そうなhookを片っ端から入れる / 起動18秒 | 「忘れちゃダメ」3つだけ / 起動5秒に維持 Layer 3 | テンプレskill 30個 / 5個しか使わない | 自分専用skill 3〜5個 / 100%動くまで磨く Layer 4 | sub-agent未活用 or 40体並列 / 1ヶ月で崩壊 | 3〜5体構成 / 役割分離 / 長期安定 数字で見ると、いちばん効くのはLayer 1です。 CLAUDE.mdをルーティング化するだけで、初期コンテキストが70%減る。 そのうえでLayer 2を絞ると、起動時間が4分の1になる。 Layer 3を「100%動く境界」で絞ると、迷いが消える。 Layer 4を「3〜5体構成」で組むと、文脈が壊れない。 「自分専用に育つ」が成立する条件 ここまで組むと、第2の脳は「使うほど自分専用に育つ」状態に入ります。 Stop hookがミスを記録する。 rules/が状況別に呼ばれる。 skillが自分の業務に特化する。 sub-agentが自分の役割分担で動く。 各レイヤーが、自分の使い方に合わせて精度を上げていく。 これがテンプレ運用ではどうしても作れない構造です。 テンプレは「みんなのため」に最適化されている。 4レイヤー設計は「自分のため」に最適化されていく。 両者は方向そのものが違う。 ここまで来ると、もうテンプレに戻れません。 ９. 12週ロードマップ — 段階導入の進め方 「4レイヤー全部いきなり組むのは無理そう」と感じる人が多いと思います。 実際、いきなりやると詰みます。 段階導入のロードマップを置いておきます。 12週で、無理なく4レイヤーを積むプランです。 Week 1〜2: Layer 1 / コンテキスト層を整える 最初の2週間は、CLAUDE.mdとの向き合い直しです。 Week 1で、いまのCLAUDE.mdの行数を数える。 200行を超えていたら、ルーティングディレクトリ化に着手。 「自分の役割」「環境」「状況別ルーティング目次」だけ残して、詳細はrules/に切り出す。 Week 2で、rules/の各ファイルを読み返して、矛盾と重複を整理。 1ファイル200行を上限に絞る。 ここが土台になるので、最初の2週間でしっかり時間をかけます。 Week 3〜4: Layer 2 / 自動化層を最小構成で導入 土台ができたら、hookを3つだけ入れます。 Week 3で、Write/Edit直後のRead強制と、危険Bashコマンドのブロックhook。 Week 4で、セッション終了時のミス振り返りhook。 ミス追記hookは、複利が効くまで1ヶ月くらいかかります。 最初の数週間は「ミスなし」が続いても、焦らない。 3週目あたりから、ちゃんとミスが拾われ始めます。 ここで「あ、システムが回ってきた」と感じる瞬間が来ます。 Month 2: Layer 3 / 機能層を1つずつ増やす 5週目以降は、skillを月に1〜2個ずつ増やしていきます。 最初の1個は、自分がいちばん時間を使っている業務を選んでください。 記事執筆、メール下書き、コードレビュー、議事録要約、リサーチ。 なんでもいいですが、「毎週やってる」業務にする。 毎週使うから、磨かれる。 毎日使うから、100%動くまで詰めるモチベーションが続く。 汎用テンプレを30個入れるより、自分専用を3個磨く方が、第2の脳としての価値が高いです。 Month 3: Layer 4 / 協調層を2体構成で試す 3ヶ月目に、ようやくsub-agentに手を出します。 最初は2体構成です。 メインClaudeが設計者。 sub-agentが実装者。 具体的には、執筆系のタスクで「構成設計はメイン」「実際の執筆はsub」みたいに分けてみる。 慣れたら、リサーチャーを足して3体構成に。 3ヶ月の終わりには、4レイヤーが揃った状態になります。 このペースで組むと何が起きるか 12週終わって振り返ると、変化が見えます。 CLAUDE.mdが3分の1くらいになっている。 rules/が状況に応じて呼ばれて、ルールが効いている。 hookでミスが自動記録されて、同じミスが減っている。 skillが3〜5個、自分のリズムで動いている。 2〜3体のagentが、役割分担で動いている。 これ、12週前の自分には作れなかった構造です。 そして、ここから先は複利で育つ。 １０. まとめ — テンプレの先で会いましょう 長くなったので、最後にまとめておきます。 第2の脳は、ツールじゃない。 入れ物でもない。 AIと一緒に、時間をかけて育てていく成果物です。 そのために必要なのが、4レイヤー設計でした。 Layer 1のコンテキスト層が、司令塔を整える。 Layer 2の自動化層が、忘れることを物理ブロックする。 Layer 3の機能層が、自分の業務を100%再現する。 Layer 4の協調層が、文脈を分離して設計と実装を分ける。 下から積む。 下層が腐ると、上層が崩壊する。 上層が育てば、下層に複利が効く。 この構造を、12週かけて自分の中に作る。 それができたあと、第2の脳は「使うほど自分専用に育つ存在」になります。 ある研究者の言葉に、こういう一文がありました。 compound interest is the secret to growth. 知識も同じです。 毎日コツコツ積めば、複利で育つ。 ただし、腐らない設計の上に積んだときに限ります。 テンプレで止まる人と、その先に行ける人の差は、ここにあります。 設計判断を、自分でやるかどうか。 ツールの選択じゃなくて、設計の話。 これが、毎日Vaultとrules/を触りながら見えてきた結論です。 この記事が少しでも参考になった方へ。 📝 要約

🎯 テンプレ導入で「動いた感」を得ても1か月で頭打ちになる。第2の脳を腐らせないには、CLAUDE.md・hooks・skills・sub-agentsを下から積む4レイヤー設計と、12週の段階導入が要る。

Layer 1 コンテキスト層／Layer 2 自動化層

CLAUDE.mdは公式推奨の200行以下に収め、役割・環境・状況別ルーティング目次だけ置き、詳細はrules/に分離（初期コンテキストが約70%減。500行超では約7割のルールが無視されるという検証記事を引用）。hooksは「忘れてはいけないこと」（危険コマンドのブロック、Write後のRead、セッション終了時のミス記録）に絞る。hook肥大で起動が4.9秒から18.2秒になる実測、hookが無音で失敗する事例があり、ログ出力を必ず仕込む。

Layer 3 機能層／Layer 4 協調層

commandsは明示的に呼ぶもの、skillsは条件で自動起動するもの。descriptionは具体的なトリガー語で書き、30個入れて実働4〜5個という状態を避け、四半期ごとに棚卸し。「100%動かない自動化は自動化ではない」。sub-agentsは文脈を分離する道具で、設計者×実装者の2体から始め3〜5体まで。AI社員40体が1か月で崩壊した事例（context rot・compaction崩壊）を警告。

💡 ゆりこの活用メモ

① 自分のvaultとの照合 CORINのCLAUDE.md・rules・hooks・skillsの肥大度を、この4レイヤーの基準（行数・起動時間・実働スキル数）で見直す材料にする。

② 注意 数値は引用元・著者環境の報告で、そのままゆりこの環境に当てはまるとは限らない。
