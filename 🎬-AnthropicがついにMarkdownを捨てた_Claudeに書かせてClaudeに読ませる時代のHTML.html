📝 要約

🎯 Anthropicのクロードコードチームのタリク・シヒパル氏が、社内のドキュメントフォーマットをMarkdownからHTMLに切り替えた理由を解説。AIが書き手・読み手になった時代に、トークン制限が消えた今、HTMLの情報密度と双方向性が「読み飛ばし」を解決する答えだという主張。

📌 ポイント

1. 編集者の消失 — Markdownの「人が編集しやすい」前提が崩れた

シヒパル氏の.mdファイルはもうクロードに書かせてクロードに編集させる運用に変わった。自分の手で直接編集する機会がほぼゼロ。さらに「100行を超えるMarkdownは自分でも読まないし、チームに共有しても誰も開かない」と明言。Markdownが選ばれてきた最大の理由＝人の可読性が、AIワークフローでは消滅している。

2. トークン制限の終わり — HTMLのタグオーバーヘッドはもう誤差

GPT-4時代のコンテキストウィンドウ8192トークンでは、HTMLのタグ分のトークン膨張が致命的だった。だが2026年4月のクロード Opus 4.7で入力100万トークン・$5/1Mトークンになり、新トークナイザーで35%増えてもHTMLオーバーヘッドは誤差範囲。Markdownを選ぶ「トークン効率」の根拠が消えた。

3. 情報密度の差 — エージェントが妥協しなくなる

HTMLは表（table）、デザイン（CSS）、図解（インラインSVG）、コード（script）、操作UI（HTML+JS）、空間データ（絶対配置/canvas）、画像（img）まで全部表現できる。Markdownしか出せないクロードは、カラーパレットをユニコードのブロック文字＋グレースケール濃淡で表現するような「歪んだ妥協」をする。HTMLを許すと、エージェントが書きたい情報を圧縮せずに渡せる。

4. 動かせる文書 — その場限りのカスタムエディタが生まれる

シヒパル氏が公開したコンパニオンサイト（tarix.github.io）には、20個の自己完結型HTMLが置かれている。チェックアウトボタンのホバーアニメ調整スライダー、Linear 30チケットをNow/Next/Later/Cutにドラッグ並べ替えするボード、プロンプトテンプレートのチューナーなど。製品にもしない、再利用ツールにもしない、その作業1回限りのために作るUIという発想。出力ボタンで結果をJSON/プロンプトとしてコピーし、クロードに戻すループが速くなる。

5. スキル化を「待て」 — まだ /html スキルを作るな

シヒパル氏は記事の最後で「/htmlスキルを作りたくなる気持ちはわかるが早すぎる」と断言。HTMLの価値はフォーマットではなく「そのHTMLで何をやらせたいか」を毎回考えること。用途依存性が高い（仕様書なら可読性、レビューなら差分注釈、デザインなら触れるノブ）。プロンプトの試行錯誤を経て自分の使い方が固まった後でスキル化を検討する。Anthropic自身がスキル機能を強く押している時期に、エンジニアが「まだスキル化するな」と公言しているのが面白い。

6. コストは正直に — 生成時間2倍〜4倍、Diff読みにくい

HTMLの最大の弱点は生成時間がMarkdownの2〜4倍かかること、バージョン管理でDiffが構造ノイズで読みにくいこと。それでもシヒパル氏が選んだ理由は「HTMLにしたことでクロードの作業に深く関与できるようになった」から。以前は計画書を読まずクロードに任せて不安だったが、今は何をしているか把握できる。読まないまま承認していた人が、もう一度読み始めるためのコストとして正当化。

💡 ゆりこの活用メモ

① 明日の朝、Armillary. 26AW提案資料をHTML出力で試作する クロードコードに「HTMLアーティファクトで作って」と一言添えて、26AW提案の構成案を作らせる。スライダーやトグルで方向性を触れるようにする。MDで「3案あります」と並べるより、実際に値を動かして見せる方が小山さんもチームも判断早い。生成時間2倍は許容範囲。

② デザインレビュー用の「動かせる仕様書」を1つ作ってみる LAVANDAボンドロシールのような版下提案で、アニメ時間・拡大率・影のぼかしをスライダーで触れるHTMLを作る。クライアントに「このスライダーで好きな値にして、最後にプロンプトをコピーして送って」と言える状態を作ると、FB往復が激減する。

③ スキル化は「型が固まってから」ルールをCORINにも適用 ゆりこは「これ便利！」→「即スキル化」のサイクルが速い。シヒパル氏の警告通り、用途依存性が高い作業（資料作成・提案書）は3〜5回プロンプトで試してパターンが固まってから .claude/skills/ に固定する。早すぎるスキル化は具体性を殺す。
