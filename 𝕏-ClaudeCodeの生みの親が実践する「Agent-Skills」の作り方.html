ClaudeCodeの生みの親が実践する「Agent Skills」の作り方

Claude Codeを作ったBoris Chernyさんが、矛盾するようなことを2つ言っています。 1つ目。Claudeがミスをしたら、その場で注意して終わらせるな。CLAUDE.mdやスキルに残せ。 2つ目。6か月ごとに、CLAUDE.mdもスキルもフックも全部消して、何もない状態で何ができるか見ろ。 育てろ、と言った直後に、捨てろと言っている。 最初に読んだとき、どっちだよと思いました。 でも調べていくうちに、この2つが完全につながっていることが分かりました。そしてここが、2026年のAgent Skillsを理解する上で一番大事な部分だと思っています。 先に結論を書きます。 すべての指示はパッチです。そしてパッチには期限があります。 モデルができなかったことを補うために書いたのがスキルです。モデルが賢くなれば、そのパッチは不要になるどころか、邪魔になります。 だから、育てながら、定期的に捨てる。 この記事では、Anthropicの公式ブログとBorisさんの発言をもとに、Agent Skillsの正しい作り方を書きます。 そして日本語でよく見る「Skillはプロンプト集」という理解が、なぜ間違っているのかも書きます。 まず、Agent Skillはマークダウンファイルではありません ここが最初の誤解です。 Anthropic自身が、公式ブログではっきり書いています。 「スキルはただのマークダウンファイルだ」という理解は、よくある誤解です。 実際は何かというと、フォルダです。 my-skill/ ├── SKILL.md ├── references/ │ ├── api.md │ └── gotchas.md ├── scripts/ │ ├── verify.py │ └── Gotcha（ガチャ）というのは、「普通にやると間違えるポイント」のことです。落とし穴。 公式が挙げている実例が、めちゃくちゃ分かりやすいので3つそのまま紹介します。 例1：テーブルの罠 subscriptionsテーブルは追記専用です。欲しい行は、created_atが最新のものではなく、versionが最大のものです。 これ、コードを読んだだけでは分かりません。 普通に考えたら「最新の日付の行」を取りますよね。でもこのテーブルの設計だと、それは間違いです。 例2：名前が違う このフィールドは、APIゲートウェイでは@request_id、課金サービスではtrace_idと呼ばれています。同じ値です。 これも、両方のコードを読まないと気づけません。 例3：嘘の成功 ステージング環境は、Stripeのwebhookが実際には処理されていなくても200を返します。本当の状態はpayment_eventsを確認してください。 これが一番怖いやつです。成功したように見えて、していない。 この3つに共通しているもの 分かりますかね。 全部、Claudeがコードを読んだだけでは絶対に分からない情報です。 そして、その会社の人間しか知らない情報です。 ここがスキルの本質だと思っています。 Anthropicはこう表現しています。 Claudeを、いつもの思考パターンから外す情報こそをスキルに入れる。 逆に言うと、こういうものは書かなくていいです。 ・変数名は分かりやすくする ・きれいなコードを書く ・エラー処理をする ・テストを書く Claudeはもう知っています。 公式の言い方だと、こうです。 Don’t state the 数行の指示と、1つのGotchaから始まった。 そして、Claudeが新しい失敗をするたびに、そこへ追加していった。 つまりスキルは、書くものじゃなくて育てるものです。 Borisさんのやり方 ここでBorisさんの話が出てきます。 Claudeが何かミスをしたとき、多くの人はチャットでこう言って終わります。 「次から気をつけて」 それだと、その会話でしか効きません。 特定の作業の手順 　→ スキルにする

絶対に守らせたいこと 　→ フックで強制する 一番下が重要です。 「絶対にやるな」を文章で書いても、破られる可能性があります。 長いセッション、曖昧な状況、外部からの変な指示。こういう場面で、指示は無視されることがあります。 本当に止めたいなら、AIの注意力に頼らず、プログラムとして止める。ここは後半でもう一度書きます。 必要なときだけ読ませる 3つ目の原則です。用語としてはProgressive Disclosure、段階的な開示と呼ばれます。 考え方はシンプルで、最初から全部読ませないということです。 スキルはこういう層になっています。 層 中身 読まれるとき 1 名前と説明文 常に 2 SKILL.md本体 そのスキルが呼ばれたとき 3 references、assets 必要になったとき 4 scripts 実行が必要なとき つまり、普段はほとんど何も読み込まれていません。 だから、SKILL.md本体には目次だけ置きます。 research-skill/ │ ├─ SKILL.md │ ├─ references/ │ ├─ source-policy.md │ ├─ fact-check.md │ └─ article-format.md │ ├─ scripts/ │ └─ verify_dates.py │ └─ assets/ └─ article-template.md そしてSKILL.mdにはこれくらいしか書きません。 一次情報を調べる必要がある 　→ references/source-policy.md を読む

ここ、日本語圏でかなり軽視されています。 Claude Codeを起動したとき、Claudeが最初に見るのは各スキルの名前と説明文だけです。 そして「今回このスキルを使うべきか」を、そこだけで判断します。 つまり、こうです。 説明文は、紹介文ではありません。検索のインデックスです。 悪い例と良い例 悪い例。 description: X記事の作成を支援する これだと、いつ使うべきかが分かりません。 というのも、Claudeはスキルを使うべきなのに使わない傾向があるからです。だから説明文は、少し積極的に書いたほうがいいです。 そして、ここに落とし穴があります これはネタ元にも書かれていなかったんですが、調べていて見つけました。 スキルとコマンドの説明文には、合計の文字数に上限があります。 既定で15,000文字、トークンに直すと約4,000です。 Anthropicは社内の数百のスキルを分類しています。ライブラリやAPIの使い方、データ分析、定型業務の自動化、テンプレート生成、コード品質、デプロイ管理、障害調査の手順書、インフラ運用。 その中で、最も測定可能な品質向上を生んでいるのが検証スキルだと明記されています。 そして、こうまで書かれています。 検証スキルを良くするためだけに、エンジニアが1週間を使う価値がある。 📝 要約

🎯 Agent Skillsは「プロンプト集」ではなくフォルダ単位の小さな業務システム。すべての指示はパッチで期限があるので、失敗のたびに育て、モデル更新のたびに一度全部外して必要分だけ戻す。

1. スキルの価値は「Claudeが知らない情報量」

SKILL.md・references・scripts・assetsを持つフォルダ構成。最も情報密度が高いのはGotchas（普通にやると間違える落とし穴）。一般論は書かず、その会社固有の罠だけ書く。最初は数行と1つのGotchaから育てる。

2. 必要なときだけ読ませる（段階的開示）

名前と説明文は常に読まれ、本体・参照・スクリプトは必要時のみ。説明文は紹介文でなく検索インデックスで、「いつ使うか」「ユーザーが言いそうな語」まで入れる。説明文の合計は既定約15,000字が上限で、超えるとスキルが黙って一覧から落ちる。

3. 検証スキルと育てて捨てるサイクル

最も効くのは、Claude自身が成果物を実際に使って答え合わせできる検証スキル。「絶対に守らせたいこと」はCLAUDE.mdでなくフックで機械的に止める。Borisは半年ごとにCLAUDE.md・スキル・フックを全削除（Ablation）し、失敗する箇所だけ戻す運用を勧める。
