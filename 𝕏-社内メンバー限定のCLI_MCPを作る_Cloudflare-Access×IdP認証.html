社内のメンバーだけがアクセス可能な CLI / MCP を作る farstep @farstep_ · 14h Follow 4 57 648 414K 現在、スタートアップで、会社を AI Ready な状態にするための基盤システムを開発しています。目的は、Claude や Codex などの AI が、人間と同じ文脈にアクセスできる状態を作ることです。そのためには、この基盤システムが人間だけでなく AI からもアクセスできる必要があります。 AI にとって扱いやすいインターフェースは CLI と MCP です。ここで問題になるのが認証の仕組みです。API キーを作成して配布する方法も考えられますが、次の課題があります。 秘密情報である API キーを AI に渡したくありません。そもそも漏洩の危険性があります。 API キーの発行・配布・保管に手間がかかります。 社員が入れ替わったときの失効や、有効期限の扱いを個別に管理する必要があります。 CLI や MCP を社内メンバーだけがアクセスできるようにするという課題は、突き詰めると「API の認証をどうするか」という問題になります。 本記事では、API キーを配布せず、API 自体を IdP 認証で保護し、その認証を CLI と MCP で共有することで、社内メンバーだけがアクセス可能な CLI と MCP を実現する構成を説明します。

何を保護するのか この基盤の本体は、業務に必要な文脈を AI が読める形で集約した API です。これにより、人間が毎回情報を探して渡さなくても、AI が自分で文脈を読みに行けるようになります。 この API は業務データの正本（source of truth）であり、業務情報を含みます。そのため、社内の人間と AI だけが、同じ認証のもとで参照できる必要があります。本記事が扱う CLI / MCP / API 基盤は、この集約した文脈への社内限定アクセス経路にあたります。

解決の方針 この構成の要点は、利用者や AI ごとに API キーを発行するのではなく、API 自体を IdP（Google Workspace 等）認証で保護し、その認証を CLI と MCP で共有することです。具体的には次の 2 点で成り立ちます。 これを実現するため、API の手前に「認証をエッジで肩代わりする層」を置き、IdP にログイン済みのリクエストだけを通します。この層として、本構成では Cloudflare Access（Cloudflare が提供する、エッジでのアクセス制御サービス）を採用します。数あるアクセス制御の手段のなかで Cloudflare を選ぶ理由は次の 3 点です。 IdP（Google Workspace 等）とそのまま連携でき、本人確認の判断を IdP に委ねられます。 cloudflared というローカルエージェントが認証トークンの取得とキャッシュを肩代わりするため、CLI も MCP も秘密情報を持たずに済みます。 API の実行基盤やデータベースも Cloudflare（後述する Workers / D1）で構築するため、認証から実行まで同一プラットフォームで完結します。 この前提のうえで、構成は具体的には次の 2 点で成り立ちます。 API を Cloudflare Access（エッジでのアクセス制御）の内側に置き、IdP で認証されたリクエストだけを通します。クライアントは Access を通過しなければ API に到達できません。 CLI と MCP サーバを同一のバイナリで提供します。どちらの入口を使っても、同じ手順で認証トークンを取得し、同じ API を呼びます。 「誰が社員か」の判断は IdP に一元化するため、入退社の反映は IdP の操作だけで完結します。

全体構成 中心にあるのは API です。CLI と MCP サーバは、その API を呼ぶ 2 つの入口にすぎません。重要なのは、CLI と MCP サーバが同一のバイナリである点です。CLI に専用のサブコマンド（例： mcp）を用意し、それを実行すると MCP サーバとして振る舞います。 この基盤は次の 3 つの要素で成り立ちます。 API（保護対象）：業務データを提供する本体です。実行基盤は Cloudflare Workers、データベースは Cloudflare D1 を使います。唯一の保護対象であり、業務データの正本です。 CLI（コマンドライン入口）：API を呼び出すコマンドラインツールです。人間がターミナルから操作するほか、シェルを扱う AI エージェントも同じコマンドを実行します。配布の単位でもあります。 MCP サーバ（AI ホスト向け入口）：MCP に対応した AI ホストから呼び出すための入口です。CLI と同一のバイナリが提供します。 入口は利用者で固定されるわけではなく、状況に応じて使い分けられます。人間は主にターミナルで CLI を使います。AI は、MCP に対応したホストからは MCP を、シェルを扱えるエージェントからは CLI を直接実行します。CLI は出力先がパイプのとき機械可読な形式（JSON）へ自動で切り替わるため、AI からも扱えます。 このため、どちらの入口も、認証・通信・データアクセスのすべてを共有します。 入口

stdio 上の JSON-RPC API は Cloudflare Access（エッジ）で保護され、その内側の Cloudflare Workers で動きます。

前提・条件 この構成を成立させるには、次の準備が必要です。 IdP（Google Workspace 等）を Cloudflare Access に連携していること。 API を保護対象とする Self-hosted Application を Cloudflare Access に作成し、アクセスポリシー（許可対象を自社ドメインやグループに限定）を設定していること。 API 側に、検証で使うチームドメイン（issuer）とアプリケーション固有の AUD 値（audience）を設定していること。 CLI を GitHub Packages（npm レジストリ）で配布するため、ソースとパッケージを GitHub の Organization 配下に置き、CI 実行基盤として GitHub Actions を利用できること。 利用者が CLI をインストールする端末に、GitHub CLI（gh）・cloudflared（Cloudflare のローカルエージェント）・CLI 実行環境（Node.js 等）を導入していること。 IdP ログインを行えない経路（外部サービスからの Webhook、外形監視のヘルスチェックなど）がある場合は、Cloudflare Access の Bypass ポリシーで対象外にできること（具体的な担保方法は後段「IdP ログインを行えない経路の扱い」で述べます）。

認証の仕組み（Cloudflare Access × IdP） リクエストは「クライアント → Cloudflare Access → API」という一方向で流れます。Cloudflare Access が IdP と連携して本人確認を担い、API は Access が保証した認証情報を受け取って処理します。 クライアントが API を呼ぶには、先に認証トークン（JWT）を取得しておく必要があります。手順は次のとおりです。 クライアントがログイン操作を行い、ブラウザを開きます。 ブラウザが Cloudflare Access 経由で IdP のログイン画面に遷移し、利用者が認証します。 認証が成功すると、Cloudflare Access が短命の JWT を発行します。 cloudflared がこの JWT をローカルにキャッシュし、以降のリクエストで使い回します。期限が切れたら再ログインで取り直します。 トークンの取得とキャッシュは cloudflared が担うため、CLI 自身は認証情報（秘密鍵やパスワード）を一切持ちません。

二段階の JWT 検証 トークン取得後の API 呼び出しでは、エッジとオリジンの二段階で検証が行われます。 クライアントは取得済みの JWT をヘッダ（cf-access-token）に載せて HTTPS で送信します。 エッジ（Cloudflare Access）が JWT を検証します。失敗すればこの時点で拒否されます。 検証に成功すると、Cloudflare Access はオリジン向けのリクエストに Cf-Access-Jwt-Assertion ヘッダを付与して API へ転送します。 オリジン（API）はこのヘッダの JWT を、Cloudflare Access が公開する JWKS（公開鍵セット、/cdn-cgi/access/certs）で再検証します。このとき署名の正当性に加え、発行者（issuer ＝チームドメイン）と宛先（audience ＝アプリ固有の AUD）が一致することを確認します。 検証に成功したリクエストだけが、API の本処理に到達します。 オリジンでも検証する理由は多層防御です。設定ミスや想定外の経路でオリジンに直接到達した場合でも、Access を経由していないリクエストを確実に弾けます。鍵は定期的に（既定では 6 週間ごとに）ローテーションされるため、公開鍵は固定値で持たず、必ず JWKS エンドポイントから取得します。

IdP を正本とするアカウント管理 この構成では、「誰が社員か」を IdP（Google Workspace）だけで管理します。Cloudflare Access も API も独自のユーザ名簿を持たず、認証のたびに IdP の判断へ委ねます。アカウント管理の窓口を IdP 一つに集約することで、次の利点が得られます。 入社時：IdP にアカウントを追加するだけで、CLI・MCP・Web のすべてにアクセスできるようになります。各システムへの個別登録は不要です。 退職時：IdP からアカウントを削除（または無効化）するだけで、すべての経路へのアクセスが即座に断たれます。Access は認証のたびに IdP を参照するため、削除されたユーザは新しいトークンを取得できず、既存の短命トークンも期限切れとともに失効します。 権限の追加・剥奪を複数システムで個別に行う必要がなく、消し忘れによる不正アクセスなどの食い違いが起きません。

CLI の配布（GitHub Packages） CLI は単一の実行ファイルにバンドルし、GitHub Packages の npm レジストリに非公開（private）パッケージとして publish します。GitHub Packages を選ぶことで、別途レジストリや認証基盤を用意せず、ソースコードと同じ GitHub の権限管理をそのまま配布のゲートに使えます。 配布の流れは次のとおりです。 リリース担当がバージョンを上げ、バージョンタグを push します。 GitHub Actions がタグ push を契機に起動し、ビルド・型チェック・publish を実行します。 利用者は GitHub の認証を通したうえで、グローバルインストール（npm install -g ）します。 接続先 API の URL は CLI に既定値を持たせ、通常は設定不要とします。別環境に向けるときだけ環境変数で上書きします。 パッケージ名は @/ の形式で、スコープ（@）を Organization 名と一致させる必要があります。これは GitHub Packages の npm レジストリの制約です。

publish 側の認証（CI） publish は GitHub Actions に自動発行されるトークン（GITHUB_TOKEN）で行います。このトークンはワークフローの実行中だけ有効で、終了と同時に失効します。権限はワークフロー定義で「パッケージ書き込み（write:packages）」のみに絞ります。 この方式により、長期間有効な API トークンを secret として保管・ローテーションする必要がなくなります。タグとパッケージのバージョンが一致することを検証してから publish し、二重 publish を防ぎます。

install 側の認証（Org メンバーシップがゲート） このアーキテクチャの要は、GitHub Organization のメンバーであることが、そのまま CLI をインストールできる条件になる点です。非公開パッケージの取得には「パッケージ読み取り権限（read:packages）を持つ Org メンバーのトークン」が必要で、Org 外の人はインストールできません。 認証情報（トークン）の渡し方は次の 2 通りで、いずれも Org メンバーシップが前提です。 動的取得（主）：GitHub CLI のログインセッションからトークンをその都度取り出し、環境変数経由で npm に渡します。設定ファイル（~/.npmrc）にはトークンそのものを書かず、環境変数を参照する記法だけを書きます。トークンをディスクに平文保存せず、GitHub のログアウトで自動的にインストールもできなくなる点が利点です。 個人アクセストークン（従）：GitHub CLI を使えない場合の代替です。パッケージ読み取り権限（read:packages）を持つ個人アクセストークンを発行し、設定ファイルに保存します。なお、クラシックトークンで非公開リポジトリと連携する構成では repo スコープも必要になる場合があるため、可能なら必要権限だけを付与できる細粒度（fine-grained）トークンを推奨します。レジストリが公式にサポートする方式ですが、有効期限の管理が必要で、ファイル権限を絞る運用が前提です。 publish 側のトークンとは異なり、install 側に書き込み権限は不要です。読み取り権限のみに限定します。

配布の制限とセキュリティ境界の関係 ここで明確にしておくべきは、パッケージの非公開化はアクセス制御の本体ではないという点です。セキュリティ境界はあくまで Cloudflare Access（IdP 認証）です。 CLI のバイナリ自体は秘密情報を含みません。仮に流出しても、IdP 認証を通らない限り API へはアクセスできません。 GitHub Packages の非公開化は、「無関係な人が CLI を入手・実行しようとする入口」を一段減らすための層と位置づけます。 結果として境界が二重になります。配布のゲートが GitHub Org メンバーシップ、API のゲートが IdP 認証で、どちらも社員名簿（IdP / Org）に紐づきます。退職時に両方の名簿から外せば、入手経路も実行権限も同時に失われます。

MCP の設定 MCP サーバは、CLI と同じバイナリをサブコマンドで起動したものです。AI のホスト（Claude Desktop / Codex CLI 等）の設定ファイルに、起動コマンドとして登録します。 json { “mcpServers”: { "": { “command”: "", “args”: [“mcp”], “env”: { “<API_URL_VAR>”: “https://” } } } } 通信方式：ホストがプロセスを spawn し、標準入出力（stdio）越しに JSON-RPC で通信します。プロトコルが流れる標準出力は専有し、ログは標準エラー出力に出します。 遅延認証：起動時には認証しません。認証起因で起動が失敗すると、ホスト側から原因を追えなくなるためです。ツール呼び出しのたびにトークンを取得し、認証エラー（401／403）を受けたら一度だけ取り直して再試行します。 読み取り専用：AI に公開するツールはデータの参照系に限定します。AI からデータを変更できないことを型レベルで保証します。 設定は起動コマンドの登録だけで完結し、AI 専用の認証情報は発行しません。AI は、その端末の利用者がすでに行った cloudflared ログインのセッションをそのまま使います。

CLI と MCP が同じ認可を共有する仕組み CLI も MCP サーバも同じ手順でトークンを取得し、同じ API を呼びます。したがって、どちらの入口を使っても、また人間と AI のどちらが使っても、同一の IdP・同一の認可経路を通って同じデータにアクセスします。AI は、それを動かす端末利用者の身元で動くため、誰の操作かが明確で、退職時の失効も人間と同時に効きます。 入口ごとに異なるのは、公開する操作の範囲だけです。MCP 経由で使える操作は公開するツール（参照系）に絞られ、CLI を直接使う場合は人間と同じコマンド範囲になります。ただしいずれの場合も、API 側の認可（同一の身元）を超える操作はできません。

IdP ログインを行えない経路の扱い 外部サービスからの Webhook や外形監視のヘルスチェックは、人間によるブラウザ認証を行えません。これらは Cloudflare Access の Bypass ポリシーで保護対象から外し、別の手段で正当性を担保します。 Webhook：送信元が付与する署名（HMAC など）をオリジン側で検証します。 ヘルスチェック：認証不要の軽量なエンドポイントを用意し、機密情報を返さないようにします。 ローカル開発でも IdP 認証を行えないため、認証をバイパスする経路を設けることがあります。この経路は本番環境に絶対に持ち込まない運用が前提です。

運用コスト 小規模な組織であれば、IdP 以外はほぼ無料で運用できます。 Cloudflare Access（Zero Trust）は 50 ユーザーまで無料です。 API の実行基盤である Cloudflare Workers と、データベースである Cloudflare D1 にも無料枠があり、小〜中規模の利用であれば無料枠に収まります。 実質的な費用は IdP（Google Workspace 等のライセンス）のみで、それも多くの組織がすでに契約済みのものを流用できます。 つまり 50 人以下の組織なら、IdP 以外に追加コストをほぼかけずに、社内限定の API 基盤を構築できます。

📝 要約

🎯 スタートアップで「会社をAI Readyにする基盤」を作っている著者が、APIキーを配布せず社内メンバー（人間＋AI）だけがアクセスできる CLI / MCP を構成する方法を解説。API自体を IdP（Google Workspace等）認証で保護し、Cloudflare Access をエッジ認証層として置く設計。

AIに秘密情報を渡したくない・漏洩リスク・発行/保管/失効の管理コスト。認証の判断はIdPに委ね、エッジ（Cloudflare Access）でリクエストを検査する。
