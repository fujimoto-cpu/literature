📝 要約

🎯 AIの精度を上げる設計手法として最近話題の「ループエンジニアリング」（時間軸で実行→検証→改善を繰り返す設計）と「グラフエンジニアリング」（構造軸で複数AIをどう配置するか設計）を、クロードコードのサブエージェント実践例つきで解説する動画。

🗺️ 全体像

flowchart TD
    A[プロンプト/コンテキスト/ハーネス設計] --> B[メインエージェントが成果物を作成]
    B --> C[別AIの検証エージェントがチェック]
    C -->|改善点を指摘| D[メインエージェントが修正]
    D --> C
    C -->|OKまたは上限回数到達| E[完成品]

📌 ポイント

1. 用語の階層 — プロンプト→コンテキスト→ハーネス

AIへの指示文の作り方が「プロンプトエンジニアリング」、指示以外に会話履歴・ウェブ検索・ファイルなど「何をいつどれだけ読ませるか」を設計するのが「コンテキストエンジニアリング」。さらにAIが動く環境（実行基盤・権限管理まで）を丸ごと設計するのが「ハーネスエンジニアリング」。クロードコードがウェブ検索やファイル実行までできるのは、このハーネスが設計されているから。

2. ループエンジニアリング — 時間軸で「実行→検証→改善」を回す

AIエージェントが何か実行し、その結果を検証し、改善案をもとにまた実行する、を繰り返す設計。Andrej Karpathy氏の「オートリサーチ」（機械学習モデルをAIが自律的に改善するプロジェクト）が話題になった例。人間の指示なしにAIが実験→改善を繰り返すことで精度が上がっていく。

3. グラフエンジニアリング — 構造軸で複数AIの配置を設計

調査を複数の観点・複数のAIで分担させ、結果を集約し、足りなければまた調査させる、というようにどのフローでどこにAIを配置するかを設計する考え方。実質は昔からある「ワークフロー」と同じで、クロードデスクトップやChatGPTのウルトラ推論モードは既にこれを内部で自動生成している。

4. 検証は自分ではなく別のAIにやらせる

言語モデルは自分が作ったものを甘く評価しがちなため、生成担当と検証担当を分けた方が精度が上がる。KAIST・カーネギーメロン大学・NVIDIAの研究では、フィードバックなしの自己修正はほとんど精度が改善しないが、別のAIが評価基準を持ってダメ出しすると（5回の修正で）94.7%まで精度が伸びた例が示されている。生成はSonnet、検証はOpus/Fableのような高性能モデルという分け方も紹介。

5. 弱点：コストと局所最適解

複数のAIモデルを使うためコスト・時間が増える。またスコアを単純に改善するだけだと、一度下がらないと辿り着けない領域（局所最適解）で止まりやすい。対策として複数のプロンプトを並列で進化させる手法もあるが、まだ確立した解法ではないと本人も述べている。

💡 ゆりこの活用メモ

① 制作物のセルフチェックを「別セッション」に分離する デザイン案・議事メモ・提案書などをCORINに作らせたら、同じセッションで「これで合ってる？」と聞くだけでは精度が上がらない（論文の「フィードバックなし修正」と同じ構造）。別チャットで「このデザイン、ダメ出しして」と検証だけを頼む一手間を、AI推進担当としての実践例として社内共有できる。

② サブエージェントの使い分けを社内AI事例に転用 reviewer サブエージェント（レビュー専任・読み取り専用）はまさに動画の「検証エージェントを分ける」構造そのもの。品質表示タグ生成ツールなど社内向けAIツールに「作る担当」と「チェックする担当」を分けて組み込む提案は、AI推進の事例としてそのまま使える。

③ ループの上限回数を決めてから走らせる 「無限に改善し続けられる」わけではなく、局所最適解にはまるリスクがある。修正ループを頼むときは「最大3回まで」のように上限を先に決めておくと、コストも時間も暴走しない。
