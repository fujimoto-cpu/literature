  1. ナレッジ管理が「業務代行」に進化した転換点 — Karpathy から cyrilXBT へ Obsidian × AI の本流は、2025年に静かに2段ジャンプしました。 第1ジャンプは Karpathy の「LLM as compiler & librarian」。Karpathy は raw articles / papers / notes を「ソースコード」、LLM を「コンパイラ」、生成されるwiki を「実行可能ファイル」と見立てました。Obsidian は単なるメモ帳ではなく、AI が読んで再構成する素材庫になる、という発想の転換です。 ここで重要なのは「ライブラリアン」のほうです。Karpathy はこう続けます。 Instead of using traditional RAG systems, the LLM acts as a full-time research librarian — actively compiling, linting, and interlinking Markdown files. LLM が司書として常駐し、Vault のメモを能動的に編成し、矛盾を検出し、リンクを張り直す。これがあると Vault は「使うほど精度が上がる」状態に入ります。 第2ジャンプが cyrilXBT の業務OS化。Karpathy が静的な3層（raw / wiki / reports）を示したのに対し、cyrilXBT は実行レイヤーまで降ろしました。 具体的には、Obsidian の上に N8N の自動化レイヤーと、Claude Code の MCP 接続を重ねて、「メモが溜まる」から「タスクが進む」に変質させた。Obsidian は素材庫から業務OS の OS 部分になったわけです。 Greg Isenberg（Late Checkout 創業者、フォロワー約50万）はこの構造をひと言でまとめています。 how to use obsidian + claude code to build a 24/7 personal operating system 「自分のための、24時間動くOS」。これが2025年後半から2026年にかけて、海外発信界隈の共通語になりました。 Tiago Forte の「Second Brain（第2の脳）」はあくまで個人の蓄積でした。cyrilXBT が「Business Operating System」と呼んだのは、その先。蓄積を超えて、事業を動かすOS に進化した、という宣言です。 Karpathy が「設計図」を描き、cyrilXBT が「自動運転の実装図」まで降ろした。本記事はその実装図を、日本の業務文脈に合わせて再配線するための地図です。
  2. 業務OS の3層アーキテクチャ — Knowledge / Intelligence / Automation cyrilXBT の業務OS は、明確に3層で構成されています。順番に分解します。 Layer 1: Knowledge（保存層）= Obsidian すべての業務情報を Markdown のローカルファイルで保存する層です。Obsidian は単なるエディタですが、ローカル Markdown という選択が決定的に効きます。 Obsidian CEO の Steph Ango はこう言い切っています。 local-first, markdown-native knowledge management ローカル優先、Markdown ネイティブ。サブスクが切れても読める。サービスが終了しても残る。10年後にも開ける。これは「自分の事業データをプラットフォームに人質に取られない」という、業務OSの大前提です。 Evernote がかつてのノート最大手から滑り落ちた話を覚えている方も多いと思います。クラウド完全依存、サーバー閉鎖リスク、プラットフォームロック。多くのパワーユーザーが Obsidian に移ったのは、業務データを自分の管轄に取り戻すためでした。 Layer 2: Intelligence（思考層）= Claude Code via MCP ここが Karpathy の言う「ライブラリアン」の住む層です。Claude Code が MCP（Model Context Protocol）経由で Obsidian の Vault を読み、考え、書き戻す。 MCPは「AI システムの USB-C」とよく例えられます。GitHub の stars は81,000を超え、OpenAI / Google / Microsoft / AWS / Meta が公式サポート。日本でも freee / kintone / LINE / Chatwork / Backlog が MCP サーバーを提供しはじめています。つまり、業務システムと AI を繋ぐ標準規格として実質決着が付いた状態。 Claude Code はこの MCP を介して Vault を「常時アクセス可能な作業領域」として扱います。ユーザーがチャットを開かなくても、Vault の Markdown を読み、追記し、再構成する。常駐司書としての性格がここで生まれます。 Layer 3: Automation（実行層）= N8N 最後の層が N8N。これが「スケジューラ兼神経系」として動きます。 N8N は2025年の JavaScript Rising Stars で1位（+112,000 stars/年）、Fortune 500 の25%が採用、合計150,000 stars 超え。ノーコード自動化の事実上の業界標準になりつつあります。日本のノーコード市場も2026年に1,330億円規模で、年率17.1%で伸びています。 役割分担はシンプルです。 思考しているのは Claude 実行しているのは N8N 保存しているのは Obsidian 3つを1つに混ぜると壊れますが、層を分けると拡張がきく。これが cyrilXBT 構成の肝です。Christopher Alarcon という Solo Founder は同じ構造を月$100で組んで、「コンテンツ再利用 → リード取得 → リサーチ自動化 → 公開承認」のパイプラインを回しています。 非同期コミュニケーションの効果は2025年の研究でも裏付けられていて、リモート環境で「生産性向上の羅針盤」と呼ばれるようになりました。3層に分けた瞬間、業務は同期から非同期に切り替わります。
  3. Vault フォルダ構造 — GENERATED と QUEUE が「非同期ループ」を作る 3層を組んだら、次は Obsidian の中身です。フォルダ構造は cyrilXBT の指定にほぼ準じて、こうなります。 Business Vault/ ├── 00 - INBOX/ ← その日の思いつきを放り込む場所 ├── 01 - CLIENTS/ ← クライアント別フォルダ ├── 02 - PROJECTS/ ← 案件・プロジェクト別 ├── 03 - OPERATIONS/ ← 経理・契約・社内運用 ├── 04 - CONTENT/ ← 投稿・記事・配信物 ├── 05 - RESEARCH/ ← リサーチ素材 ├── 06 - PEOPLE/ ← 関係者・取引先 ├── 07 - SYSTEM/ ← CLAUDE.md・ログ・設定 ├── 08 - GENERATED/ ← ★ AIが書き出した成果物 ├── 09 - QUEUE/ ← ★ AIへの依頼ファイル置き場 └── 10 - ARCHIVE/ ← 凍結・終了 注目してほしいのは GENERATED と QUEUE の2つ。ここが業務OSの心臓部です。 普通のメモアプリは「自分が書く / 自分が読む」の同期ループしか持っていません。一方この2フォルダは、自分とシステムの非同期ループを作ります。 QUEUE は「やってほしいことを置く場所」。客先訪問の事前ブリーフが欲しい、投稿の下書きが欲しい、競合のニュースを朝までにまとめておいてほしい。そういう依頼を、自分の都合のいいタイミングで放り込む。 GENERATED は「やった結果が降ってくる場所」。N8N が定期的に QUEUE を覗き、Claude に渡し、結果を GENERATED に書き出す。自分は朝に受け取って、必要なら確認するだけ。 cyrilXBT 本人がこう書いています。 You capture tasks when they occur to you. The system executes them when it runs. You review results when it is convenient. タスクは思いついた瞬間に捕まえる。システムは自分のスケジュールで動く。結果は自分の都合のいいときに見る。3者が一切お互いを待たない。 この発想は、日本のメモ管理本にはほとんど登場しないものです。日本では「メモは見返すもの」「振り返るもの」が主流で、「メモは処理してもらうもの」という発想がほぼ存在しない。ここに業務OSの本質的な飛距離があります。 Noah Vuong というブロガーは491個のPermanent Notesを Vault に置き、Claude Pro €20/月で「2分で Newsletter ドラフト完成」「2分で SOP 完成」を実現しています。低投資・高ROIの典型例。 逆に cyrilXBT 自身、半年前は2,000ノートを溜めただけで何も見つからない「ノート地獄」状態だったと振り返っています。 Six months ago my Obsidian vault had 2,000 notes and I could not find anything. I rebuilt the entire structure in one afternoon using this exact system. I have not lost a single idea since. 午後1回分の構造再構築で、それ以来1つのアイデアも失っていない。蓄積は構造がないと負債になる。先に骨を入れる、というのが cyrilXBT のメッセージです。
  4. CLAUDE.md は「業務憲法」である — テンプレと Weekly Focus の威力 3層と Vault 構造が組めたら、次がいちばん効くやつです。 07 - SYSTEM/ フォルダに CLAUDE.md を置きます。これは自分の事業ルールを全部 Markdown 化した、いわば業務憲法。すべての自動化ワークフローは、何をする前にこのファイルを読みます。 Anthropic 公式が出した「Claude Code Best Practices」でも、CLAUDE.md は context そのもの だと位置付けられています。雑に書かれた CLAUDE.md からは雑な出力しか出てこないし、精密に書かれた CLAUDE.md は、Claude を「自社の業務を熟知した担当者」に近づける。 Anthropic 社内の Data Infrastructure チームは、リポジトリの CLAUDE.md に「データパイプラインの保守ルール」を集約して、新機能実装・テーブル依存関係の把握・ドキュメント生成まで Claude に任せています。従来「データカタログ」と呼ばれていたツールが、CLAUDE.md 一枚で置き換わった、という社内事例です。 ベーステンプレはこう書けます。

Business Operating System — CLAUDE.md

事業の定義

  • 事業名: 〇〇
  • 提供価値: 〇〇
  • 顧客像: 〇〇
  • 収益モデル: 〇〇
  • フェーズ: 立ち上げ / 成長 / 安定

アクティブクライアント

  • {クライアント名}: {契約形態} / 現状: {状態} / 次のアクション: {具体}
  • {以下、案件ごとに}

アクティブ案件

  • {案件名}: 概要 / 現状 / 締切 / 次のマイルストーン
  • {以下、案件ごとに}

文体・トーン

  • 書き方: 〇〇調、〇〇な雰囲気
  • 絶対に使わない表現: 〇〇 / 〇〇
  • CTA の型: 〇〇

収益目標

  • 月次目標: {金額}
  • 現状 MRR: {毎月更新}
  • 注視している主要指標: {1つだけ書く}

投稿運用

  • 配信頻度: {例: 平日3本}
  • コンテンツ柱: {主軸テーマ3〜5個}
  • フォーマット: {長文 / 短文 / 図解 など}

運用ルール

  • ファイルを削除しない。タイムスタンプ付きでアーカイブする
  • 顧客向け文面は人間レビューなしで送らない
  • 生成ファイルは YYYY-MM-DD でタイムスタンプ
  • すべての書き込み操作を SYSTEM/logs/operations.md にログ
  • 不確実なときは GENERATED に置いてフラグを立てる
  • 金銭・契約・関係性・評判が絡むものは必ず人間にエスカレ

今週のフォーカス

{毎週月曜の朝に更新する。今週いちばん大事なこと} 最後の「今週のフォーカス」セクションが、いちばん効きます。 月曜の朝に2分かけて「今週いちばん大事なこと」を書き換える。それだけで、その週に動くすべての自動ワークフローが現在の優先順位に沿った出力を返すようになります。朝のブリーフの粒度、コンテンツ提案の角度、リサーチの掘り方、全部が今週のテーマに寄っていく。 Karpathy の「ライブラリアン」概念がここに重なります。CLAUDE.md は、Claude というライブラリアンに渡す「館内ガイド」。これがないと司書は「一般論で並べたメモ」しか返してくれない。これがあると「あなたの事業のためにキュレーションされたメモ」を返してくる。 5. 6つの業務システム（前半）— 法人案件運用の3システム ここから本丸の6システムです。cyrilXBT は順に6つを並べていますが、日本の事業主の運用優先度に合わせて、ここでは法人案件運用群と個人発信運用群の2つに分けて並べ直します。 法人案件運用群は3つ。クライアントを抱えている人、案件で動いている人、お金が複数の口座を行き来する人にとって、いちばん早く効くはずです。 システム1: Client Intelligence（クライアント情報層） 役割は2つあります。 ひとつ目は 客先訪問30分前の事前ブリーフ自動生成。N8N が Google Calendar を見て、訪問予定の30分前に発火します。Claude が 01 - CLIENTS/{クライアント名}/ を全部読んで、ブリーフを GENERATED に書き出してくれます。 プロンプトはこんな形です。 01 - CLIENTS/{クライアント名}/ の中身を全部読んでください。 以下を5分で読める粒度で1枚にまとめてください:

  • 関係性の経緯（重要な出来事と判断を時系列で）
  • 現在のエンゲージメント状況
  • 未対応の約束（こちらが提示したまま動いていないこと）
  • 直近のやり取り（日時 / 媒体 / 主旨）
  • 先方が大事にしていること
  • 今回の打ち合わせの推奨アジェンダ 3点
  • 今回必ず伝えること 1点 保存先: 08 - GENERATED/briefings/{日付}-{クライアント名}-precall.md 「客先に向かう電車で目を通す5分の事前ブリーフ」を、自動で前日の23時に作っておく。これだけで、商談の密度が変わります。 ふたつ目は コミュニケーション・ロガー。日次メモに「{クライアント名}と{要件}でやり取り」と書いたら、Claude が要点を抽出して 01 - CLIENTS/{クライアント名}/communications/ に追記する。 書くのは1回。整理は自動。 システム2: Project Operations（案件運用層） 役割は 朝の案件パルス。毎朝6時、N8N が 02 - PROJECTS/ を全部覗いて、状況サマリを GENERATED に置きます。 02 - PROJECTS/ の全ファイルから「完了していない」案件を読んでください。 各案件について以下を出してください:
  • 案件名 / クライアント
  • 現在のフェーズ
  • 昨日完了したこと（昨日の日次メモから抽出）
  • いま詰まっていること
  • 次にやることと担当者
  • 締切までの残り日数 以下のいずれかに該当する案件にはフラグを立ててください:
  • 締切まで7日以内で未完タスクあり
  • 同じステータスのまま5日以上動いていない
  • 詰まりがあるのに解決策が書かれていない 保存先: 08 - GENERATED/briefings/{日付}-project-pulse.md 朝の4分で全案件の状態が把握できる。これがあるとないとでは、案件の遅延検知速度が決定的に変わります。 加えて 完了マーカーによる自動更新。日次メモに DONE: {案件名} — {成果物} と書けば、Claude が該当案件のタスクリストを自動で更新します。書くのは1回。更新は自動。 システム3: Financial Operations（財務運用層） 入金記録の RECEIVED: ¥{金額} — {クライアント} — {内容} という1行を日次メモに書く運用にする。あとは N8N が毎月1日に動いて、その月の財務サマリを GENERATED に書き出します。 {先月} の全日次メモから RECEIVED 行を抽出してください。 03 - OPERATIONS/finances/expenses/ から経費記録を読んでください。 CLAUDE.md から月次目標を読んでください。 財務サマリを出してください:
  • 売上 vs 目標（パーセンテージ）
  • 前月比較
  • クライアント別売上内訳
  • 主な経費カテゴリ
  • 純損益
  • このパターンが続いた場合の翌月予測 保存先: 08 - GENERATED/reports/{日付}-financial-brief.md それから毎月25日に 請求リマインダー。継続案件の入金状況を見て、未入金のクライアント宛て請求書ドラフトを GENERATED に置く。自分は承認するだけ。 Anthropic 自社のエンジニアは Claude Code 経由でタスクの60%を回し、平均50%の生産性向上を達成しています。大学レベル相当の複雑タスクでは12倍の速度向上、というデータも出ています。法人案件運用の3システムは、まさにここに刺さる領域です。
  1. 6つの業務システム（後半）— 個人発信運用の3システム 後半の3つは、発信・リサーチ・振り返りに効くやつです。発信を続けている人、情報を扱う仕事をしている人、自分の意思決定の質を上げたい人向け。 システム4: Content Production（コンテンツ生産層） 毎朝、3つが動きます。 朝のコンテンツブリーフ。直近48時間のリサーチブリーフ、自分の日次メモのアイデア、コンテンツカレンダー、CLAUDE.md のコンテンツ柱を全部読んで、その日に書ける角度を3本出してくれる。 以下を読んでください:
  2. 08 - GENERATED/briefings/ の直近48時間のリサーチブリーフ
  3. 直近の日次メモに書き留めたアイデア
  4. 03 - OPERATIONS/content/calendar.md の予定トピック
  5. CLAUDE.md のコンテンツ柱 以下を出してください:

  1. 自動化レイヤー — N8N の3トリガーで全部を繋ぐ ここまでの仕組みは、N8N が3種類のトリガーで動かします。 Cronトリガー — 時間で発火するやつ。朝6時のブリーフィング、日曜夜8時の週次レビュー、毎月1日の月次レポート、25日の請求リマインダー。スケジュールが決まっているものはここ。 File Watchトリガー — Vault のフォルダ変化で発火するやつ。QUEUE に新しいファイルが置かれたらキュー処理ワークフローが動く。案件フォルダの更新を見て、関連する案件マスタを書き換える。「ユーザーが書いた瞬間にシステムが動く」型はここ。 Webhookトリガー — 外部イベントで発火するやつ。Stripe で新規入金があったら売上トラッカーが更新される。Google Calendar に新しい予定が入ったら客先ブリーフが起動する。「外で起きたことを Vault に取り込む」型はここ。 すべての N8N ワークフローは、共通の骨格を持ちます。 Trigger → CLAUDE.md を読む → 関連する Vault コンテンツを読む → コンパイルしたコンテキストで Claude API を呼ぶ → 結果を Vault に書き出す → 通知を送る（Telegram / Slack / メール） → 操作ログに追記 肝は、Claude API 呼び出しのシステムコンテキストに、必ず CLAUDE.md の中身を含めること。これがあるとないとで、出力の業務特化度が完全に変わります。 N8N は2025年に Fortune 500 の25%が採用するレベルまで普及し、日本のノーコード市場も17%/年で伸びている。$5/月の自前ホスティングで無制限のワークフロー実行ができるので、コスト面でもボトルネックになりません。 n8n 公式のテンプレート集には「Gmail + Google Calendar + 天気API → Claude API → Telegram 朝6時送信」の Morning Brief テンプレが既にあって、コピペで動かせます。
