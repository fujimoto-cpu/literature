「新しいプロジェクトにアサインされて、まず数万行のコードを Claude Code に読ませたら、それだけでトークンを使い切ってしまった」 「Skill を入れたいのに、GitHub をあちこち探して手動でコピーして、結局どこに置いたか分からなくなった」 このあたりで消耗している人は、たぶん多いと思います。僕も少し前まで、巨大なリポジトリの全体像をつかむために片っ端からファイルを読ませて、コンテキストウィンドウ（AI が一度に扱える入力の上限）が埋まってきて精度が落ちる、という往復をやっていました。 最近やり方が変わったのは、Claude Code の「Skill（スキル）」を2つ入れてからです。ひとつは Graphify。コードベースを丸ごと読ませる代わりに、一度だけ解析して「ナレッジグラフ（どの関数がどこで呼ばれ、どのファイルが中心かを表した地図）」に圧縮してくれる Skill です。公式が看板に掲げている例では、コードと論文を混ぜた約52ファイルのコーパスで、1回の問い合わせが平均1.7千トークン（素朴に読ませると約12.3万トークン）まで圧縮され、71.5倍の削減になったと報告されています（Graphify 公式サイト）。もうひとつは npx skills。世界中で公開されている Skill を1コマンドで探して入れて更新できる CLI（コマンドラインツール）です。 この2つを軸に、Skill とは何か、正しいインストール手順、自分で書ける汎用 Skill の例、運用上の落とし穴までを、公式の一次情報で確認しながら整理します。出回っている誇張した売り文句はいったん脇に置いて、何ができて何ができないかを具体で書きます。 tatsuki（@nobel_824）と申します。中小企業向けに AI の活用サポートをしていて、Claude / Codex の業務導入を手伝いつつ、自分でも Claude Code を1日中走らせています。「AI に丸投げして高い・遅い」をどう減らすかは、サポートの現場でもよく出るテーマです。

  1. そもそも Skill とは何か。なぜトークン節約に効くのか まず前提を揃えておきます。Claude Code の Skill とは、特定のタスクのやり方や役割を、あらかじめ Markdown ファイルに書いて持たせておく拡張のしくみです。.claude/skills/<スキル名>/SKILL.md という場所に置き、ファイルの先頭に name と description を書いた frontmatter（YAML 形式のヘッダ）、その下に手順を書きます（Claude Code 公式ドキュメント）。 最小の中身はこれだけです。

name: release-notes description: git の履歴からリリースノートを書く。リリース準備のときに使う

リリースノート作成

直近のタグからの commit を集めて、ユーザー向けの変更点を箇条書きでまとめる。 なぜこれがトークン（料金や処理量の単位になる入力の量）の節約につながるのか。理由は、毎回プロンプトに長い指示を書き直さなくてよくなるからです。「どう振る舞ってほしいか」を Skill 側に固定しておけば、本番では短い一言で同じ品質の動きを呼び出せます。誰がやっても同じ手順を踏ませられるので、再現性も上がります。 つまり Skill は「AI に毎回ゼロから説明する」のをやめて、「役割と手順を持った専門家を呼ぶ」に切り替える道具です。この発想を踏まえると、次の Graphify が効く理由も分かりやすくなります。 今日できる1アクション：自分が Claude Code に毎回ほぼ同じ言い回しで頼んでいる作業をひとつ思い出してください。それが最初に Skill 化する価値のある候補です。

  1. Graphify：コードベースを「読む」から「地図を引く」に変える 巨大なプロジェクトでまずやるのは全体像の把握ですが、数万行を AI に読ませるのは現実的ではありません。Graphify はここを解決する Skill です。 Graphify が何をするか Graphify はコードや設定、ドキュメント、PDF などをスキャンして、ナレッジグラフを1回だけ作ります。どの関数がどこから呼ばれているか、どのモジュールが中心（依存が集まる「god ノード」）か、どのファイルが関連の塊（コミュニティ）を作っているかを構造として持ち、以降は生ファイルを読み直す代わりにこの地図をたどります。解析には Tree-sitter（コードを構文単位で読む解析器）や NetworkX、Leiden クラスタリング（グラフの構造だけでまとまりを見つける手法）といった技術が使われていて、公式サイトでは19言語のソース解析に対応すると説明されています（Graphify リポジトリ / Graphify 公式サイト）。 プライバシー面で大事な点として、Graphify が AI モデルに送るのはドキュメントや図の「意味の要約」だけで、生のソースコードそのものは送らない設計になっています（Graphify リポジトリ）。 コスト削減の数字を正しく押さえる よく出回っている「コストを71.5分の1に」という数字は、どういう条件で出た値かを押さえておいた方がいいです。これは公式サイトが看板に掲げているベンチマークで、GPT フレームワークのリポジトリ3本＋論文5本＋図4枚を混ぜた約52ファイルのコーパスに対し、1回の問い合わせが平均1.7千トークン、素朴に全部読ませると約12.3万トークン、その比が71.5倍という内訳です（Graphify 公式サイト）。あくまで特定コーパスでの値なので、自分のプロジェクトで同じ倍率が出ると約束されたものではありません。公式は別の例として、約50万語規模のコーパスでも問い合わせを約2千トークンに保てたと紹介していますが、いずれも「条件つきの上限寄りの値」として見ておくのが安全です。 インストールはこの順番（npx ではない） ここは間違えやすいところです。Graphify は Python 製のツールで、npx skills のような Skill 管理 CLI 経由ではなく、PyPI（Python のパッケージ配布先）から入れます。公式パッケージ名は graphifyy（末尾の y が2つ）で、似た名前の別パッケージは無関係だと明記されています（Graphify リポジトリ）。

1. パッケージを入れる（PATH を自動で通してくれる uv が推奨）

uv tool install graphifyy

uv が未導入なら、公式サイトと同じ pip でも入る

pip install graphifyy

2. Claude Code に Skill として登録する（ここまではターミナルで打つ）

graphify install

3. ここからは Claude Code など AI アシスタントの中で打つ

/graphify . 最初の2行はターミナルでの操作、最後の /graphify . は Claude Code の中で打つコマンドです。/graphify . を打つと、graphify-out/ フォルダに3つのファイルができます。ブラウザで開いて節点をクリックできる graph.html、要点をまとめた GRAPH_REPORT.md、そして問い合わせ用の graph.json です。以降は graphify query “認証はどこで処理してる？” のように、グラフに直接質問を投げられます（Graphify リポジトリ）。 チームで共有したいときは、リポジトリ単位で入れる —project を付けます。これで .claude/skills/graphify/SKILL.md がプロジェクト内に書かれ、commit して配れます。 graphify install —project 今日できる1アクション：手元の中規模リポジトリでひとつ、uv tool install graphifyy → graphify install → /graphify . まで通して、GRAPH_REPORT.md を開いてみてください。自分のコードの「中心ファイル」がどこか、地図で見える感覚が掴めます。

  1. npx skills：Skill を探す・入れる・更新するを1コマンドに Skill は世界中の開発者が日々公開していて、GitHub を手で探して配置するのは骨が折れます。ここを引き受けてくれるのが、Vercel が公開している npx skills（vercel-labs/skills）という CLI です（vercel-labs/skills）。

基本はこの1行 npx skills add <owner/repo> GitHub の owner/repo を渡すだけで、その中の Skill を自分の環境に入れられます。フル URL やローカルパスも渡せます。対応エージェントは Claude Code・Codex・Cursor・OpenCode をはじめ50以上で、入れ先も自動で判別してくれます（vercel-labs/skills）。Claude Code の場合はプロジェクト直下の .claude/skills/ に入ります。

探す・一覧・更新もコマンドで完結します。 npx skills find typescript # キーワードで Skill を探す npx skills list # 入っている Skill を一覧 npx skills update # 入れた Skill を最新版に更新 「Skill を探したい」と思ったときは、公式ディレクトリの skills.sh を見るのが早いです。npx skills の中には find-skills という、この skills.sh をエージェントに検索させる Skill も入っていて、AI 自身に「この用途に合う Skill ない？」と探させることもできます（find-skills）。 チーム共有は lock ファイルではなく「scope と更新」で考える 出回っている解説には「skills-lock.json で共有する」と書いてあるものがありますが、npx skills の公式 README にそのファイルは出てきません。実際の共有のしかたは、プロジェクト単位（デフォルト）で .claude/skills/ に入れて、それをリポジトリと一緒に commit する、という形です。入れ方は symlink（元の1か所を参照する）か copy を選べて、更新は npx skills update で揃えます（vercel-labs/skills）。チーム全員が同じ Skill 構成で動くようにしたいなら、ここを押さえておけば十分です。 今日できる1アクション：npx skills find を一度だけ叩いて、いま自分が手で繰り返している作業に近い Skill が公開されていないか覗いてみてください。自分で書く前に、既にある知見を1つ借りるところから始めると速いです。

  1. 自分で書ける汎用 Skill の例（explain / summarize / quiz） 外から入れる Skill だけでなく、日々の作業を楽にする小さな Skill は自分で数行書けます。第1章の SKILL.md 形式そのままで作れるので、よく使う3つの型を例として置いておきます。これらは「有名な配布 Skill」ではなく、自分の .claude/skills/ に置く自作テンプレの一例として読んでください。

explain：他人のコードを3層に分けて読み解く 数か月前の自分が書いた謎のロジックや、引き継いだコードを、ただ翻訳するのではなく「何のための処理か」まで含めて説明させる Skill です。SKILL.md の本文にこう書いておきます。 渡されたコードを「ビジネスロジック」「エラーハンドリング」「パフォーマンス上の懸念」の 3つに分けて、それぞれ日本語で説明する。なぜこの実装にしたのかの推測も添える。

summarize：技術ドキュメントを決まった型で要約 README や公式ドキュメントを読む時間を縮めるための Skill です。出力の型を固定しておくと、毎回同じ密度で読めます。 渡したドキュメントを「重要ポイント3つ」「最短セットアップ手順」「注意すべき制約」の 3ブロックで要約する。一次ソースの URL があれば末尾に残す。

quiz：理解度のセルフチェックを作らせる 新しいライブラリを学ぶとき、学んだ範囲から確認クイズを作らせると「分かったつもり」が早めに分かります。 直前の会話で学んだ内容から、理解度を確かめる質問を5つ作る。 答えは伏せて出し、頼まれたら解説する。 今日できる1アクション：上のどれか1つを .claude/skills/explain/SKILL.md のように保存して、実際のコードで呼んでみてください。型を決めて出力させるだけで、AI の返しのばらつきが減るのが分かります。 5. 運用で踏みやすい3つの落とし穴 便利な反面、先に知っておくと事故りにくい注意点が3つあります。 ひとつめはコストの読み違いです。Graphify の「71.5倍」も npx skills の手軽さも、効くのは条件が揃ったときです。Graphify は最初のグラフ構築に解析コストがかかり、小さなリポジトリだと素直に読ませた方が速いこともあります。倍率はあくまで特定コーパスでの上限寄りの値として見て、自分のプロジェクトで実測してから判断するのが安全です。 ふたつめはセキュリティです。npx skills add は他人のリポジトリの中身を自分の環境に持ち込みます。SKILL.md は AI への指示書なので、入れる前に中身を一度読んで、不審な操作（鍵の送信や広範囲の削除を促す指示など）が書かれていないか確かめた方がいいです。Graphify のように生ソースを送らない設計かどうかも、外部ツールを入れるときの判断材料になります。 みっつめは再ビルドと共有のずれです。Graphify のグラフはある時点のスナップショットなので、コードが大きく変わったら作り直さないと地図が古くなります。npx skills もメンバーごとに別々に入れると構成がずれるので、プロジェクト単位で .claude/skills/ を commit し、npx skills update で更新を揃えるのを習慣にしておくと、チームでの食い違いが減ります。 今日できる1アクション：外部 Skill を入れる前に、その SKILL.md を1ファイルだけでいいので開いて読む、を自分のルールにしてみてください。 6. 中級者向け補足：素の grep/Read との使い分けと、よくある疑問 最後に、もう一歩踏み込んだ疑問を補足します。 Q. Graphify は素の grep や Read と何が違う？ ファイル単位で読む grep/Read は「どこに何があるか」を都度探しますが、Graphify は「どの関数がどれに依存しているか」という関係をグラフとして先に持っておきます。公式は、グラフを入れると検索やファイル読みの前にグラフ側へ問い合わせるよう促すフックを Claude Code 向けに用意していて、graphify query のような絞った問い合わせを優先させると案内しています（Graphify リポジトリ）。 素の Read/grepGraphify得意なことピンポイントの文字列・特定ファイルを探す依存関係や全体構造を俯瞰する事前準備不要グラフ構築が1回必要小さなリポジトリそのままで十分速い構築コストの方が重いこともある大きなリポジトリ読むほどトークンが膨らむグラフをたどるので軽い 広く構造を見たいときはグラフ、ピンポイントの文字列を探すだけなら grep、と使い分けるのが現実的です。 Q. npx skills と Claude Code のプラグインは別物？ 別の枠組みです。npx skills はエージェント横断で Skill を配布・管理する CLI で、配置先の .claude/skills/ は Claude Code の標準の Skill 置き場です。npx skills は .claude-plugin/marketplace.json のようなプラグイン定義も読み取れるので、プラグインのマーケットと共存できる作りになっています（vercel-labs/skills）。 Q. 結局どのくらいのエージェントで使える？ npx skills は Claude Code・Codex・Cursor・OpenCode を含む50以上のエージェントに対応しています。Graphify も Claude Code・Codex・OpenCode・Cursor・Gemini CLI など複数のアシスタントで動きます（vercel-labs/skills / Graphify リポジトリ）。特定のクライアントに縛られない作りなので、Codex と併用していても同じ Skill を共有できます。 Q. Codex で Graphify を使うときの注意は？ Codex では /graphify ではなく $graphify を使い、~/.codex/config.toml の [features] に multi_agent = true を足す必要がある、と公式が補足しています（Graphify リポジトリ）。クライアントごとに起動の書き方が少し違う点だけ気をつけておくと迷いません。 まとめ：全部読ませる人から、地図を引いて聞く人へ この2つの Skill で変わるのは、AI への向き合い方だと思います。巨大なコードを毎回頭から読ませて消耗するのではなく、一度グラフにして必要な部分だけ聞く。Skill を手で探して散らかすのではなく、1コマンドで入れて更新を揃える。要点を並べておきます。 Skill は .claude/skills/<名>/SKILL.md に役割と手順を持たせるしくみで、毎回の長い指示を減らせる Graphify はコードをナレッジグラフに圧縮する Skill。uv tool install graphifyy（または pip install graphifyy）→ graphify install → /graphify . で使う（npx 経由ではない） 公式の看板値は約52ファイルのコーパスで「71.5倍」のトークン削減。条件つきの上限寄りの値として見る npx skills は Skill の発見・導入・更新を1コマンドにまとめる CLI。50以上のエージェントに対応 explain / summarize / quiz のような小さな Skill は自分で数行書ける 落とし穴はコストの読み違い・外部 Skill の中身確認・再ビルドと共有のずれ 今日から試す3ステップ [ ] 中規模リポジトリで uv tool install graphifyy → graphify install → /graphify . を通し、GRAPH_REPORT.md を開く [ ] npx skills find で、自分の作業に近い公開 Skill をひとつ探す [ ] explain / summarize / quiz のどれかを .claude/skills/ に保存して、実際のコードで呼ぶ 定型的な解析や探索を Skill に預けたとき、空いた時間で何を考えるか。そこが、これからいちばん人に残る仕事になっていくのだと思います。 参考リンク（公式一次ソース） Graphify リポジトリ（safishamsi/graphify。インストール手順・対応言語・プライバシー設計） Graphify 公式サイト（71.5倍のトークン削減ベンチマークと Worked Examples） vercel-labs/skills（npx skills の全コマンドと対応エージェント一覧） skills.sh（公開 Skill を探せる公式ディレクトリ） Claude Code Skills 公式ドキュメント（SKILL.md の仕様）
