ClaudeCode×Obsidian×Codexはいいぞ。

Claude Code を私の業務脳として常駐させ、その Claude Code から複数の Codex に作業を振る体制を作ってみました。正直言ってめちゃくちゃ良かったので、興味ある人は是非真似してみてください！

人間が毎回すべてを説明し、AI にひとつずつ作業を頼む形ではありません。私の事業文脈、判断基準、過去の失敗、投稿ルール、ナレッジ管理の型を Claude Code に読ませておきます。そのうえで、Claude Code が「これは分けられる作業だ」と判断したものを Codex に配り、Codex が各自の作業を終えて戻ってきます。

今日のセッションでは、この構造で既存の有料記事をインデックス化し、たまっていた未処理素材の一部を並列でナレッジ化しました。直列でやると重い作業が、同時進行でかなり前に進みました。

なお本記事で扱う Claude Code と Codex の運用は、AI駆動塾メンバーシップで実装の中身まで共有しています。月額4,980円で、有料記事の読み放題、月次セミナー、Discordでの質問対応、希望者には個別セットアップ伴走までついています。「自分の事業で同じ構造を作りたい」という人はこちらをどうぞ。

メンバーシップ： https://bit.ly/ai_kudoujuku

全体像

この構造で大事なのは、Claude Code と Codex に別々の役割を持たせることです。

Claude Code は、私の脳に近い場所を担当します。AI駆動塾が何を扱っているのか、どんな読者に向けて発信しているのか、どの投稿フォーマットが過去に機能したのか、どの表現を避けるべきか。そういう前提を持ったうえで、今やるべき作業を判断します。

一方で Codex は、作業員として動きます。ひとつの素材を読む。記事を分類する。タグを付ける。ナレッジノート候補を抽出する。完了したら決められた形式で報告する。こうした、独立して進められる作業に強いです。

そこで Claude Code を間に置きます。人間が直接 Codex に毎回長い指示を書くと、どの素材を渡すか、どのルールを読ませるか、終わった結果をどう検証するかを、毎回人間が考えることになります。

Claude Code には、私の業務ルールと SkillGraphs （詳しくはこれ読んで。）読ませます。SkillGraphs は、Obsidian のウィキリンクで知識ノードを結ぶナレッジネットワークです。単なるメモ置き場ではなく、AI が必要な知識を探索できる外部記憶として使っています。仕組みの詳しい解説は上記リンクの記事にまとめています。

Claude Code はこの前提を使って、Codex 用の作業指示書を作ります。Codex はその指示書だけを読んで、自分の担当分を処理します。戻ってきた結果を Claude Code が検査し、問題があれば弾き、通るものだけを採用します。

この形にすると、人間の仕事はかなり絞られます。私は「この方向で進める」「ここは違う」「この結果は採用する」といった判断に集中できます。素材を開いて、読み、メモし、整形し、リンクを確認するような手作業は、作業員側に渡せます。

ポイントは、AI をひとつの相談相手として使うのではなく、役割を分けた小さな組織として使うことです。私は事業オーナーとして、方針を渡し、成果物を確認します。

用意するもの

道具は4つです。

  • Claude Code - Anthropic のターミナル型エージェント。指揮者役
  • Codex CLI - OpenAI のターミナル型エージェント。作業員役
  • Obsidian - SkillGraphs を構築する Markdown ボールト
  • Google スプレッドシート - 数値データ（X インプや note 売上等）の記録場所（これは任意。）

Claude Code は、フォルダ内のファイルを読んだり、コマンドを実行したり、複数ステップの作業を進めたりできます。私の場合、事業の記憶を読ませる中枢として使っています。

Codex CLI もファイルを読み書きできますが、今回の使い方では「独立した作業員」として起動します。Claude Code からブリーフを渡され、そのブリーフに沿って処理し、結果をログやファイルに残して終わる役割です。

Obsidian は、複数の Markdown ファイルをウィキリンクで結びつけてローカルでナレッジを管理するアプリです。私はここに SkillGraphs を構築しています。

SkillGraphs はそれ自体が私の業務データそのものです。事業前提、投稿ルール、過去の知見、原子的ナレッジノート、未処理素材のキャプチャ、過去記事の在庫が、すべて Markdown ノードとしてウィキリンクと領域マップで網状に結ばれています。私の業務に関わる情報はほぼ全て、この一枚の網の中で動いています。だから Claude Code や Codex は Obsidian のフォルダを読むだけで、私の事業判断に必要な文脈にアクセスできます。

数値データだけは別軸です（あと任意です。）。X のインプ、プロフィール訪問、note 売上、メンバー新規・離脱は Google スプレッドシートに毎日記録しています。これは SkillGraphs の外にあるソースで、セッション開始時に Claude Code が自動取得します。

AI に判断させたいなら、AI が読める場所に現実の在庫を置く必要があります。業務知識は SkillGraphs（Obsidian）、業務数値は Google スプレッドシート。この2軸を AI から読める状態にしておくのが、構造の前提です。

Step 1: 自分の脳をClaudeCodeに移植する

最初にやることは、Claude Code に毎回同じ説明をしなくて済む状態を作ることです。

AI に仕事を頼むとき、多くの人は毎回プロンプトで背景を説明します。「私はこういう事業をやっています」「読者はこういう人です」「この表現は避けてください」「このフォーマットにしてください」という説明です。短い作業ならそれでもいいのですが、日々の業務に使うなら限界があります。

毎回説明する情報は、毎回説明するべきではありません。ファイルにしておくべきです。

私のナレッジシステムでは、ルートに CLAUDE.md という運用指示があります。ここには、AI駆動塾の事業前提、投稿作成のルール、ナレッジノートの書き方、やってはいけないことがまとまっています。Claude Code は起動時にこのファイルを自動で読み込み、作業の前提として握ります。

同じ内容の AGENTS.md も並走させています。これは Codex が自動で読みに行くファイル名で、後ほど作業員側にも同じルールを効かせるためのものです。

さらに self というフォルダがあります。ここには identity、methodology、goals といったファイルがあり、AI が自分の役割と現在の活動スレッドを思い出せるようになっています。

フォルダの見え方は、だいたいこういう構造です。

たとえば、X投稿を書くタスクなら、いきなり本文を書き始めません。まず X運用マップや投稿フォーマットの知見を読み、過去に全件書き直しが発生した原因を踏まえて、チェックリストを通します。

ここで重要なのは、単なるプロンプト集ではなく、更新され続ける外部記憶として置くことです。

今日のセッションでも、過去記事の場所、無料記事と有料記事の違い、未処理素材の状態、ナレッジ化のルールを先に確認させました。ファイルとして読ませたうえで作業させると、AI が「なんとなくそれっぽいこと」を言う確率が下がります。

私の SkillGraphs では、ひとつのノートにひとつの知見だけを書きます。タイトルは「X戦略」や「Codex」ではなく、「無料コンテンツで具体的手順を見せることが有料会員への最短導線になる」のように、文章として機能する主張にします。ノート同士はウィキリンクでつながり、領域マップから辿れるようにします。

これにより、Claude Code は必要な知識を検索しやすくなります。単に大量のメモがあるだけでは、AI はどこを読めばいいか迷います。主張単位で整理され、マップから辿れる状態になっているから、作業前に必要な文脈を取り出せます。

「脳を移植する」と言っても、人格をコピーする話ではありません。事業判断に必要な前提を、AI が読める形で置いておく話です。最初は CLAUDE.md のような一枚の運用メモだけでも十分です。そこに失敗、ルール、判断基準を足していきます。

この段階を飛ばして Codex を並列起動しても、速度だけが上がります。速く間違えるだけです。先に Claude Code 側の脳を作るから、作業員を増やしたときに品質が崩れにくくなります。

Step 2: Codexを作業員として雇う

Claude Code に脳を持たせたら、次は手を増やします。ここで Codex（CodexCLIをインストールしてClaudeCodeがCodexを触れる状況を作る）を使います。

Codex は、ひとつの作業を任せて完了させるのに向いています。素材を読ませ、ルールを渡し、出力形式を指定すると、別のコンテキストで処理して、結果を残して終わります。Claude Code の会話コンテキストを消費し続けずに済むのが大きいです。

ここで地味に効いてくるのが、Step 1 で並走させた AGENTS.md です。Codex は CLAUDE.md ではなく AGENTS.md を自動で読みに行く仕様なので、AGENTS.md に同じ運用ルールを置いておくと、作業員側も Claude Code と同じ前提で動きます。ブリーフの冒頭で「まず AGENTS.md を読め」と指定するだけで、ノートの書き方、避けるべき表現、出力形式といった共通ルールが効きます。

今日の作業では、Claude Code が Codex 用のブリーフを作りました。ブリーフとは、作業指示書です。ここが雑だと Codex はズレるので、具体的に書きます。

ブリーフには次のような内容を入れます。

  • 読むべきルールファイル
  • 対象素材のパス
  • 抽出条件と出力形式
  • やってはいけないこと
  • 完了報告の書式

例えば、ナレッジ分解を頼むブリーフの抜粋はこんな形です。

実際には、ここに「既存ノートと重複する主張を作らない」「description はタイトル以上の文脈を追加する」「業務上出してはいけない具体数字を出さない」といった条件も足します。

起動は Bash でバックグラウンド実行するだけです。

これを並列で叩けば、複数の Codex が同時に動きます。素材の重さ、認証状態、今のマシン負荷を見ながら、同時に走らせる数を調整します。

完了報告の形式も決めておきます。ここを決めないと、ログを読む側の Claude Code が毎回「終わったのか、途中なのか、何を作ったのか」を解釈する必要があります。

作業員を増やすときに怖いのは、結果の品質が見えなくなることです。そこで Claude Code 側に検査役も持たせます。

私が見ている検査項目は、だいたい決まっています。

  • ログにエラーが残っていないか
  • 完了マーカーが出ているか
  • 成果物が指定パスに存在するか
  • タイトルが主張になっているか
  • 内部リンクが壊れていないか
  • 業務数字が紛れていないか

この検査を人間が全部やると、結局そこで詰まります。だから Claude Code が一次検査をします。人間が見るのは、合格した成果物と、判断が必要な差分だけです。

ただし、Codex に判断を丸投げするわけではありません。Codex は作業員です。作業の目的、判断基準、合格条件は Claude Code が渡します。その Claude Code の前提を最終的に握っているのは私です。

この関係を崩さないことが重要です。人間が全部やるのでもなく、AI に全部任せるのでもない。私が事業の方向を持ち、Claude Code が作業設計と検査を担い、Codex が個別タスクを処理する。今日の並列稼働は、この分担がはまった事例でした。

変化が一番わかりやすかったのは、有料記事のインデックス化です。

私はこれまで、自分が書いた有料記事を「だいたい頭に入っている」状態で運用していました。X投稿を書くときも、「この話題なら、あの記事に誘導できるかもしれない」と記憶を頼りに探していました。これだと、古い記事や関連度の高い記事が普通に抜けます。

今日のセッションでは、手元の有料記事を Codex に渡し、タイトル、URL、公開日、要旨、想定読者、タグを整理したインデックスにしました。人間が一つずつ開くのではなく、Codex が読み、分類し、一覧にしました。

これで、Claude Code が投稿案を作るときに「この投稿の読者に合う有料記事はどれか」を探せるようになりました。非エンジニア向け、Codex 向け、Claude Code 向け、事業づくり向けといった切り口で、過去記事を在庫として扱えます。

これは地味ですが、かなり大きいです。記事を書いても、次の発信に使われなければ資産として働きません。インデックス化すると、過去記事が導線の部品になります。

もうひとつは、未処理素材の並列分解です。

私は日々、海外のAI活用事例、Xで見つけた投稿、YouTubeの内容、ツールの発見などをキャプチャしています。ただ、保存しただけの素材は価値になりません。読んで、分解して、ナレッジ化する必要があります。

この処理は重いです。ひとつの素材から何を抽出するかを判断し、既存ノートと重複しないかを確認し、主張タイトルに直し、description を書く。丁寧にやると時間がかかります。

今日のセッションでは、未処理素材の一部を、複数の Codex に分けて処理しました。それぞれが別の素材を読み、AI駆動塾の事業レンズで使える知見を抽出しました。Claude Code はログを確認し、エラーやリンク破損がないかを見ました。

ここで効いたのは、作業が互いに独立していたことです。ある Codex が海外事例を読んでいる間に、別の Codex は別素材を読めます。しかも、それぞれが同じ AGENTS.md と同じ出力ルールを読んでいるので、成果物の型がそろいます。

直列だと重い作業が、同時進行で進みます。この差は時短だけではありません。未処理素材を事業ナレッジへ流し込める状態に変わります。

AI駆動塾サブスクで扱っていること

AI駆動塾のサブスクでは、私が書いた有料記事を読み放題で読めます。月次のセミナーもあり、Discord で直接質問できます。希望者には、Claude Code や Codex、SkillGraphs の個別セットアップも伴走します。

今回の記事で書いたような、Claude Code に事業文脈を読ませ、Codex を作業員として動かす構造は、実際に私が日々の運用で使っているものです。ツールの紹介だけではなく、業務に入れるためのブリーフ作成、ログ検査、ナレッジ化の型まで扱います。

📝 要約

🎯 Claude Codeを判断・指揮の中枢、Codexを独立タスクの作業員として分け、obsidianのナレッジ基盤と接続すると、素材処理や記事インデックス化を並列で進められる。

役割分担がAI運用の品質を決める

この記事の中心は、AIを単体の相談相手ではなく、小さな組織として使う発想。claude-codeには事業文脈、判断基準、投稿ルール、過去の失敗を読ませ、何を誰に任せるかを判断させる。一方でCodexは、素材を読む、分類する、タグ付けする、ナレッジ候補を抽出するといった独立作業を担当する。人間は毎回細かく説明するのではなく、方向性の判断と成果物の採用可否に集中できる。

Obsidianを外部記憶にすると作業員を増やせる

obsidian上のSkillGraphsには、事業前提、投稿ルール、過去記事、未処理素材、ナレッジノートがMarkdownノードとして蓄積される。Claude Codeはこの外部記憶を参照してCodex向けのブリーフを作り、CodexはAGENTS.mdや個別ルールを読んで処理する。出力形式、禁止事項、完了マーカーをそろえることで、並列実行しても成果物の型が崩れにくい。

未処理素材と過去記事が事業資産に変わる

実例として、有料記事のタイトル、URL、公開日、要旨、想定読者、タグをCodexに整理させ、Claude Codeが投稿案を作る際に過去記事を導線として探せる状態にした。また、海外AI事例やX投稿、YouTube内容などの未処理素材も複数Codexで分解し、事業に使える知見としてナレッジ化する。重要なのは速度だけでなく、保存した素材を再利用可能な在庫へ変えること。

💡 Creative Direction Note

CDとしての視座

CDの本質は「役割設計」 = AI時代に強い職能になる 記事の「Claude Code = 指揮者・Codex = 作業員」の構造は、実はCDが現場でやってる「ディレクター・デザイナー・カメラマン・スタイリストの役割分担」と全く同じ。CDのコア能力＝役割設計力 が、そのままAI運用にスライドできる。ゆりこの強みが時代に合致してる。

「外部記憶を整える人」が最終的にCDの差を生む SkillGraphsの考え方は、CDのリファレンス管理（過去案件・トレンド・引き出し）と同じ。Obsidianに事業文脈・案件知見・業界トレンドを蓄積していくほど、AI出力の質が上がる＝ゆりこのCD出力の質が上がる。今のCDナレッジシステム整備は地味だが効くインフラ。

「型を作る」がCDの最大の生産性 記事の核は「ブリーフ・出力形式・禁止事項を型化したから並列が機能する」。CDも同じで、kemio・Armillary.・Father Brandそれぞれに「ブリーフテンプレ・OK/NG基準・トーン定義」を作っておくと、AI併用でも別案件でも品質が崩れない。型化を後回しにしないこと。
